## 一之补、会话总结怎么用

### 单位是"一次开机"，不是"一天"

因为你的机器不是每天定点开——是为某个任务开机、做完就关。所以所有时间边界都来自系统事件日志（开机 6005 / 关机 6006），**不依赖任何时钟定时**。

### 生成一份

```powershell
cd E:\AI\voice
.\.venv\Scripts\python.exe vdigest.py --brief      # 导出事实清单（秒级）
```

`--brief` 只做采集和提炼，不调模型，跑完会把清单写到
`reports\2026-10-24_0842.brief.txt`。**然后把清单交给对话里的模型写叙述**——这一步快且质量高。

其它用法：

```powershell
.\.venv\Scripts\python.exe vsession.py             # 看所有会话（开机—关机）
.\.venv\Scripts\python.exe vdigest.py --prev       # 上一次已结束但没总结的会话
.\.venv\Scripts\python.exe vdigest.py --llm        # 用本地模型写（慢，几分钟，兜底用）
```

### 一份总结长什么样

**主体是"总账"：每次开机一段话，最新在最上面。**

```
## 2026年10月24日 周六　08:42 开机 · 至今仍在用 · 已 9 小时 17 分

这天早上八点四十二开的机，到这会儿已经九个多小时。不过从开机到下午
三点一刻，电脑上什么也没留下——录制程序那会儿还没装好。

真正的活从三点开始：先架好屏幕录制，让它自动截图、自动认出屏幕上的字；
接着花两个多小时把"听"接通……傍晚做的是"认人"——把你自己的声音建成
一份档案……中间屋里那通关于退滤芯的电话也被记下来了。

想看细节：完整记录 · 17:23 的录音 · 17:21 的录音 · 当时的屏幕
```

- **只有一段话**，不列文件清单、不写"产出"标签。文件名越复杂越没人看。
- 末尾那串是**能点开的链接**：完整记录、当时的录音（点开就播）、当时的截图。
- 那段话由对话里的模型写。要重出一次：

```powershell
.\.venv\Scripts\python.exe vdigest.py --paragraph-file reports\2026-10-24_0842.para.txt
```

- 完整记录（含文件清单、时间线）在 `reports\<日期>_<开机时刻>.md`，供点进去细看。
- 没人写稿时，兜底段落只描述"在哪些软件里操作、录到几段说话"，**绝不罗列文件名**。

### 关于"记录缺口"

每份完整记录末尾都会写清哪段时间没数据、哪些数据源不可用。**不假装记录完整。**

### 关于走神的时间（刷手机、等任务）

等一个长任务的时候人会走开刷手机，那段时间的声音对"干了什么"没有信息量。
但全部删掉又不诚实 —— 那段时间确实存在。

所以处理成**一句话**：

> 中间有大约 50 分钟（从 14:20 起）电脑一直没动过，像是在抖音上刷——
> 猜是在用手机打发等待时间，这段只记一句，不展开。

**怎么判断的**（这是关键，因为它直接决定会不会冤枉你）：

| 条件 | 作用 |
|---|---|
| 电脑屏幕这段时间**完全没有变化** | 必要条件。Windrecorder 只在画面变了才落新帧，帧与帧之间的空档就是"没人动电脑" |
| 这段时间有声音，且累计够长 | 排除"人在外面"（完全无声就不算走神） |
| **旁证**：BGM 声学事件 / 转写里出现抖音快手这类词 | 有了才敢说"在放视频" |

**只有前两条时不猜。** 只会说"电脑没动过、有声音，分不清是家里人说话还是在放东西"。

> 这里我改过一次：最初把"声纹不是你本人"也当成"在放视频"的证据，
> 结果家里人在客厅聊天会被记成"你在刷抖音"——把家里人当成了手机。
> 现在"不是本人"只能推出"屋里有别人在说话"，推不出"在放视频"。

**还有几个刻意的处理**：

- 走神时段的录音**不给链接**（最长的那段也不给），因为你说过不想回头细听
- 走神时段的说话内容**不逐条列出**，只折进那一句话
- 节目内容、时间点、情绪都不描述 —— 只记"那会儿我不在电脑前"

### 关于模型

那段话可以由两种模型写，实测差别很大：

| 谁写 | 耗时 | 质量 |
|---|---|---|
| WorkBuddy 的在线模型（在对话里让 AI 写） | 几秒 | 最好，懂来龙去脉 |
| 本机 gemma4-12b | **2~5 秒** | 够用，但文笔机械，不会联想 |
| 程序自己拼（都没模型时） | 0 秒 | 只有干巴巴的事实，读着像报表 |

现在的默认策略是：**开机那次自动总结走本地模型**（无人值守时也能出东西），
你在对话里问的时候我再写一份更好的。

> 之前本地模型要跑 400 多秒，不是模型慢，是**输出格式选错了**。
> gemma4 是"思考型"模型，默认会先长篇大论地想，想完了才写答案；
> 再加上要求它输出 JSON，等于让它逐字数括号。现在关掉思考（`think:false`）
> 只让它写一段散文，同一件事从 420 秒降到 4 秒。这是本次最大的一处修复。

手动让本地模型写一次：

```powershell
.\.venv\Scripts\python.exe vdigest.py --llm
```

不想用模型（纯事实）：

```powershell
.\.venv\Scripts\python.exe vdigest.py --no-llm
```

## 二、这套东西现在长什么样

```
开机登录
   ├─ WorkBuddy                      自启，用来在对话里写那段话
   ├─ Ollama                         自启，本地大模型（写总账那段话）
   ├─ voice_daemon.py                自启，守护进程，掉了会自己拉起
   │    ├─ voice_recorder.py         一直听着，切句，存 wav + 写库
   │    ├─ voice_asr.py              盯着新段，转写 + 情绪 + 声纹，写库
   │    └─ vsnap.py                  每 5 分钟扫一次，每小时存一张屏幕小图
```

三套东西**各写各的库，互不干扰**。语音侧只读挂载 Windrecorder 的库来做时间对齐，绝不写它。

（原来打算用计划任务，但本机安全策略把 `schtasks` 拉黑了，Run 键更省事也更透明。）

加 `--cold` 会把进程全杀掉、按开机的方式重新拉起来，真验一遍。
**关机前跑一次，比事后猜要强得多。**

**双击 `E:\AI\voice\stop_voice.vbs`**，或者在 PowerShell 里：

### 5.3.1 开机自启（已经装好了）

| `Ollama` | 本地大模型（不装这条，总账会退化成机器拼的干巴句子） |

**WorkBuddy 不用我们管** —— 它自己早就往同一个位置写了一条
`WorkBuddy.WorkBuddy`，开机本来就会起来。所以总结这件事是自动的：
下次开机会自动出上一次的那段话，不需要你先打开哪个程序。

看现在装了什么：

```powershell
.\.venv\Scripts\python.exe install_autostart.py --list
```

卸掉（比如以后不想要了）：

```powershell
.\.venv\Scripts\python.exe install_autostart.py --remove
```

装回去：

```powershell
.\.venv\Scripts\python.exe install_autostart.py
```

> 在**任务管理器 → 启动应用**里能直接看到、能直接右键禁用，比快捷方式还透明。

### 5.6 什么声音会被记下来（三道门）

录音器不是"有声就存"，它要判断这段里有没有人在说话。判断分三层，
**前两道任意一道通过就留下，第三道再复查一遍是不是人声**：

| | 门槛 | 看重什么 | 典型场景 |
|---|---|---|---|
| **严门** | 语音帧占比 ≥ 65% | 说得够清楚 | 你对着电脑说话 |
| **放宽门** | ≥ 1.5 秒 **且** rms ≥ 1000 **且** 占比 ≥ 30% | 够响够长 | 外放新闻、视频、音乐 |
| **人声门** | 谐波性 ≥ 0.45 | 有没有声带振动 | 把风扇、空调挡在外面 |

日志里每段落盘都带标记，一看就知道走的哪道：

```
段 #615  15.06s  rms=2045 语音占比=0.82 [严]  185520_750.wav
段 #701   8.30s  rms=1580 语音占比=0.47 [放宽] 190215_331.wav
```

**为什么要有第二道门**：2026-10-24 晚上放了一段越南新闻，占比只有 49%，
卡在 65% 下面，结果 7 分钟音频被整段删掉，一个字没留。原因是
"外放的声音"比"你近讲"天然模糊一截，用同一个标准必然误杀。

**第三道门是怎么来的**：2026-10-25 凌晨发现识别结果全线崩掉，一查才明白 ——
webrtcvad 只会说"这一帧响不响"，说不出"这是不是人说话"。机箱风扇、空调
这类稳态噪声能量足、连续不断，前两道门它都能混过去，于是段永远关不掉，
一路撑到上限被硬切开。回放 240 段真实录音，规律很干脆：

    段长 < 8 秒   → 有识别出字 69%
    8 ~ 15 秒     → 31%
    > 15 秒       → 12%

所以除了把单段上限从 30 秒收到 **12 秒**，还加了这道谐波性判据：
人说话时声带周期性振动会在自相关 2~12 毫秒的滞后区间上顶起一个峰，
风扇噪声没有。阈值 0.45 的实测效果是**清掉 93% 的无效段、留住 88% 的有效段**，
单段只要 25 毫秒。

另外两处配套改动：段到上限时会在末尾 400 毫秒里挑**能量最低的一帧**落刀
（不把字拦腰斩断，砍下来的那截接着开下一段）；送进模型前做一次
掐静音 + 高通 + 归一化，把远场拾音的电平拉回模型熟悉的区间。

**如果发现某类声音还是被漏记**，改 `config.json` 里这几个数（改完重启）：

```json
"loud_voiced_ratio": 0.30,   // 调低到 0.20 更宽松
"loud_rms": 1000.0,          // 调低到 600 收更轻的声音
"loud_min_s": 1.5,           // 调低到 1.0 收更短的
"min_harmonicity": 0.45,     // 调低到 0.35 更容易放行（噪声也会跟着进来）
"max_segment_s": 12,         // 单段上限
```

调完记得看一眼 `recorder.log` 里丢弃的段数有没有暴涨 ——
暴涨说明噪声也进来了，该往回调。

### 5.6b 人类活动声：啼哭、走动、挪凳子、水龙头（2026-10-25 新增）

上面三道门解决的是"别把噪声当说话"，但顺手也把一类**有价值的声响**
关在了门外：挪动凳子的吱嘎、走动的脚步、水龙头的流水，全是宽带非谐波，
人声门一律当噪声丢掉。现在多了两级专门认它们：

```
第一级 · DSP 粗筛（录音进程里，20ms/段）
    没过人声门不要紧，再看三个特征：脉冲个数（脚步/敲击/水滴）、
    单个重击的上升沿、高频占比+持续度（水流嘶声）。
    像人类活动就不丢，打上 flag='event' 落库；不像照旧丢。
    三条规则宁可错放 —— 键盘会被放进来，但那只是多花一秒推理。
第二级 · AST 精筛（转写进程里，约 1s/段）
    MIT/ast-finetuned-audioset，AudioSet 527 类，映射成中文标签：
    小孩啼哭、走动/脚步、吱嘎摩擦声、刮擦声、碰撞声、敲击声、
    门响、开合柜橱/抽屉、水龙头流水、倒水声、水流声……
    风扇、白噪声、键盘、鼠标这些明确不认。
```

**实测准确率**（72 条 ESC-50 公开样本，每类 3 条）：

| 声音 | 结果 |
|---|---|
| 小孩啼哭 | 3/3 认成「小孩啼哭」 |
| 走动脚步 | 3/3 认成「走动/脚步」 |
| 倒水 | 3/3 认成「水流声」 |
| 挪动/刮擦（手锯代理） | 3/3 认成「摩擦声」 |
| 敲门 | 3/3 认成「敲击声」 |
| 门吱嘎 | 2/3 认成「门响」 |
| 键盘/鼠标/风扇/风/雨/洗衣机/引擎 | 0 误报（一个活动标签都不出） |
| 抽水马桶声 | 认不出（模型顶分只有 0.05）——这类不硬凑 |

**在总账里长什么样**：节点「语音」那行会多一句"另录到活动声：敲击声 1 次"
（本地模型写稿时也会带上），展开明细里是「08:18 活动声（敲击声）」，
后面的「可点开」里能直接听原始录音。SenseVoice 自带的哭笑咳标签
（`<|Cry|>` 等）也会合并进来，但实测它在啼哭上 0/3 触发，主力是 AST。

**在哪调**：`config.json` 里 `event_min_score`（标签置信度下限，默认 0.10，
调低会开始收引擎/冲水这类没把握的猜测）；粗筛子阈值在 `vevents.py` 的
`SCREEN_DEFAULTS` 里（不写配置也有默认值）。模型留空 `event_model: ""`
就整体关掉精筛，只剩粗筛（粗筛放行的段将不再定名、也不会显示）。

**复现测试**：`python test_events.py`（合成信号 + ESC-50 真实样本）、
`python test_e2e_events.py`（走完整落库链路）、
`python test_ledger_events.py`（验总账渲染）。

另外时间轴相关：`node test_serpentine.js`（换行落位）、
`node test_timeline.js`（展开/收起时轴线不断）。

搜索相关：`python test_search.py`（索引、文字稿、链接全部落得到文件）、
`node test_search.js`（日期解析、关键词打分、结果渲染，跑的是页面里
那段真实 JS）；改完解析规则后再跑一遍 `node probe_search.js`，
拿线上真实数据人肉确认没跑偏。

### 5.7 截图为什么没有空白桌面了

Windrecorder 每小时截一张**全屏**。所以早先的总账里，截图经常是这个样子：
左边是干活的窗口，右边一大片是桌面壁纸（麋鹿、河、树林）—— 那是无效画面。

**为什么不改成"只截活动窗口"**：Windrecorder 确实有那个开关
（`record_screenshot_method_capture_foreground_window_only`，官方默认还是
`true`，你机器上被人设成了 `false`）。但它的代价是**同时开两个窗口时只截
有焦点的那一个**——你平时就是左右两个 WorkBuddy 窗口对着干，改成窗口模式
等于自己砍掉一半记录。所以这条路不走。

**实际做法：照旧截全屏，展示时把空白裁掉。**

判据是**灰度双峰度**，不是亮度也不是梯度 —— 这两样都分不开壁纸：壁纸是
照片，有山有天空有树林，亮度颜色都很丰富，拉伸压缩后梯度也不低。真正的
区别在**黑白分明**：窗口里全是文字、图标、按钮，一个 40 像素的小块里往往
同时踩着黑字和白底，灰度直方图呈双峰；壁纸的灰度是连续的，单峰。实测三张
截图：内容区双峰度 16~30，壁纸区 2~3，一条阈值就能切开。

裁法：按 40 像素分块算双峰度，阈值取"均值减半个标准差"（壁纸块占多数，
均值被拉低，减半个标准差正好落在两个峰的中间），再做行/列投影取内容块的
外接矩形。投影只认成片的 —— 某行的内容块数不到最大值 1/5 就不算内容行，
专门剔掉壁纸里那几块高对比区域。

| 情况 | 裁前 | 裁后 |
|---|---|---|
| 显示器关着（虚拟桌面 2400×675） | 窗口挤在左下一角 | 2400×675 → 1260×672 |
| 显示器开着、单窗口 + 桌面 | 2400×1350 | 内容铺满，不裁 |
| 左右两个窗口 | 右边半幅壁纸 | 两个窗口都留住，壁纸切掉 |

三条保证：

- **原图永远不删**。裁出来的副本叫 `HH-00.crop.jpg`，原图 `HH-00.jpg` 就躺在
  旁边；胶囊里除了截图本身还挂一个弱化的"原图"小链，裁错了随时能核对。
- **裁不出来就当没裁**。内容铺满全屏的图（比如全屏看文档）裁完还剩 85% 以上，
  这时直接保留原图，链接照原图走。
- **只在原图变新时才重裁**。实时模式每 5 分钟刷新一次，不判 mtime 的话每轮
  都把历史截图重算一遍。

### 5.8 存多久，会不会被删

**文字永久，音频也永久。** 两个都不会自己消失。

| | 保留期 | 谁来管 | 体积 |
|---|---|---|---|
| **转写文字**（`voice.db`） | **永久** | 没有任何代码会删它 | 11.6 字节/秒，一年约 30 MB |
| **录音音频**（`.wav`） | **永久** | `vclean.py --audio-days`，默认 0 = 不删 | 31.8 KB/秒，一天 2 小时约 230 MB，一年约 84 GB |

**文字比音频小 2800 倍**（实测 5.7 分钟录音 = 10.6 MB 音频 = 4 KB 文字）。
所以就算哪天真的要腾空间，删音频也永远比删文字划算 —— 音频删了文字还在，
总结、检索、时间线全都不受影响。

唯一会自动清音频的情况：**磁盘剩余低于 50 GB**（`--audio-free-gb`）。
那时才按"90 天前的先删"兜底，防止把盘撑爆。E 盘现在剩 3.1 TB，
按每天 2 小时人声算够存三十多年，正常永远碰不到这条。

> **2026-10-24 修正的一个隐患**：`vclean.py` 的 `--audio-days` 原来默认 **7 天**，
> 而 `vsnap` 每 6 小时自动跑一次 `vclean.py --apply`（不带参数）—— 等于录音
> **录完 7 天就自动删掉**，而配置文件里写的 `audio_keep_days: 60` 从来没被引用过。
> 两处对不上，且删得悄无声息。现在默认改成 0（永久），并把那个无用的键标了注释。

想手动清历史音频（比如只想留最近半年）：

```powershell
.\.venv\Scripts\python.exe vclean.py --audio-days 180           # 先看，不删
.\.venv\Scripts\python.exe vclean.py --audio-days 180 --apply    # 真删
```

**注意**：`vclean.py` 只删 `.wav`，**永远不会碰 `voice.db`**。
音频删了，转写文字、声纹、时间线仍然完整。

### 5.9 总账长什么样（S 形时间轴，一天一个点，点开才看明细）

打开 `E:\AI\voice\reports\总账.html`，页面上是一根**S 形（蛇形折返）的轴**，
轴上的节点是"一天"：

```
   ① 10 月 24 日 周六 ──────→ ② 10 月 23 日 周五 ──┐
                                                    ↓
   ④ 10 月 21 日 周三 ←────── ③ 10 月 22 日 周四 ←─┘
```

**默认就只看到这些**：一天一个点，每个点带一行"这天干了啥"，**看不到任何事件明细**。

那行摘要是**当天最新一场那段总述的第一句**（模型写段落时第一句本来就是主线），
压到 50 字以内。它不是拼接的节点标题 —— 那种拼法出来的是
"查看 README 并静默运行录音、排查网络请求被拒…" 这种流水账碎片。

#### 为什么是 S 形

最开始是一根**竖直**的轴。在 4K 上问题很明显：整页拉成一条细长的竖带，
左右两侧各剩近 1000 像素纯黑 —— 屏幕宽度根本没用上。

S 形的做法是：节点排成**网格**，轴线顺着行之间的通道来回折返
（第一行从左往右，第二行从右往左，依次交替）。**屏幕越宽，一行放得下的
天就越多**，黑边自然就没了：

| 视口宽度 | 一行放几天 |
|---|---|
| < 860px | 1 天（退化成一根左侧的竖轴，手机上就是这个样子） |
| 860 ~ 1399px | 2 天 |
| 1400 ~ 2099px | 3 天 |
| 2100 ~ 2999px | 4 天 |
| ≥ 3000px | 5 天 |

版心也从固定 940px 改成 `min(98vw, 3600px)`，4K 上直接铺满。

#### 轴是怎么走线的

- 每个格子左边留出一条 44px 的**轨道走廊**，格子顶部留出 46px 的**通道**；
  圆点骑在走廊中线上，轴线就在走廊和通道里走，**不穿过任何卡片**。
- 折返点是自动的：走完一行，顺着这一列往下落到下一行，再反向走回来。
  **折行的规矩是"新行的第一个点落在上一行最后一个点的正下方"** —— 所以一行
  没排满时，节点是往折返那一头齐（不是往左齐）。列数由浏览器实测的网格列数
  决定（`getComputedStyle`），不靠猜断点。
- 轴是一条 SVG 折线，由页面里的脚本在载入和改变窗口大小时按圆点的真实
  位置重画；首次载入时线会从起点"画"出来（1.2 秒）。
- 窗口窄于 780 像素时自动退化成"轴在左、内容在右"的单边排法。

#### 展开的时候线会不会断

不会 —— 这是专门治过的。轴线的"生长动画"是用 `stroke-dasharray`
（虚线）做的，而虚线图案是按**当时的路径长度**量好的。可展开一天会把下面
的行整个顶下去、页面长出滚动条时列宽也会收窄，**路径一变长，多出来那截
正好落进虚线空隙里**，线就断成一截一截，最后一个点看着像没连上。

所以脚本改成：动画播完（1.4 秒）**立刻把虚线撤掉换成实线**；这期间几何
要是有任何变化，也马上转实线，不硬撑。另外配了 `ResizeObserver` 兜底 ——
凡是能让布局变动的事情（内容长高、滚动条出现、字体到位）都会重画轴线，
不再依赖"猜一个足够长的刷新时长"。

**点一下这一天**才展开：当天的事件变成**卡片网格**横向铺开（屏幕越宽一行
放得越多，不再是往下摞成一条），再点一次收起。展开状态记在浏览器里，
5 分钟自动刷新之后仍然保持展开，不会把你踹回去。

当天的事件**也是倒序**：离现在最近的节点在最上面。每个节点四个部分 ——

| 行 | 内容 |
|---|---|
| **屏幕** | 在用什么软件、屏幕上是哪份文档或哪类内容 |
| **电脑日志** | 这段时间存了或改了哪些文档、改了什么 |
| **语音** | 在放视频、听音乐，还是跟人说话，大致在聊什么 |
| **可点开** | 这一段自己的录音、这一小时的屏幕小图、这一段改过的文档 |

屏幕小图点开是**裁掉空白桌面后的版本**（旁边有个弱化的"原图"可以核对），
裁切的道理见 5.7。

**证据跟着时段走**：21:26 的录音就挂在 21:16–21:30 那个节点底下，不会
一股脑堆在页面末尾。屏幕小图只挂真正落在这一段里的整点图，不硬凑。

节点怎么切：屏幕活动本身就是"同一软件连续在用"，天然一段；
短于 8 分钟的小动作（开一下资源管理器、弹个窗）并到邻居，不单独成节；
实时模式下最后一段不足 15 分钟时并进前一段 —— 十分钟的碎段模型手里
没料，写出来必是"软件正在运行"这种空话。
没有屏幕记录但还在开机的长空档，单独成节并**如实写"没有记录"**。
一次开机最多 9 个节点，再多就按时间就近合并 —— 总账不该变成流水账。

每块文案由本地模型读当天事实后写，写不出来时退化成程序拼的句子（干巴但不编）。
想强制不用模型：`vdigest.py --boot <时间> --no-llm`。

**那些小胶囊为什么一定点得开**：页面里所有链接都是**相对路径**，指向
`reports\ev\` 下的真实文件（`ev/audio/…`、`ev/shot/…`、`ev/doc/…`）。

- `ev\audio`、`ev\shot` 里的东西是**硬链接**，指向 `data\audio`、`data\snapshots`
  的原件。硬链接在 NTFS 上就是"同一份数据多一个名字"，**不额外占空间**，
  删链接也不影响原文件。
- `ev\doc` 里是文档：md 会被转成同名的 html（`使用手册-docs.html`），
  读起来像网页，不再是下载一堆文本。

为什么要多这一层：总账有时是从**预览窗口**打开的，那个静态服务很挑 ——
带 `..` 的路径 403、目录联接 403、`.md` 后缀 404，只有真实躺在 `reports`
下面的文件才给。硬链接正好满足，还不用复制一遍占空间。

`reports\ev` 可以随时整个删掉（不伤原件），下次生成会自动重建。

#### 大白话直接搜（2026-10-25 新增）

页面最上面有一个搜索框，**不用记格式，大白话直接打**：

| 你可以这么问 | 它会理解成 |
|---|---|
| 查查 10 月 25 日我做了什么 | 日期 = 10 月 25 日 → 列出那天的全部录音、屏幕记录和当天摘要 |
| 25 日 | 同上（月份默认取最新那个月） |
| 昨天 / 前天 / 周五 | 相对日期，按总账里最新的一天推算 |
| 10-24 / 10/24 | 也认 |
| 我记得我看过越南改革的事，帮我找找当时的录音 | 关键词「越南改革」→ 命中屏幕标题和 OCR，**并把那段时间前后的录音一起带出来** |
| 窗帘 / 敲击 | 命中录音文字、活动声标签 |

输入框下面那行小字是**它对你这句话的理解**（日期 + 关键词），一看就知道
有没有会错意。按 `/` 随时聚焦搜索框，`Esc` 清空。

结果分三块：

- **当天** —— 命中日期的摘要卡片，点"打开这天"会自动展开并滚到那一天的节点；
- **录音与文字稿** —— 每条一段录音：时间、时长、说话人、活动标签、命中片段
  （关键词高亮），下面两个入口：**▶ 录音**（直接放）和**文字稿**；
- **屏幕上的内容** —— 窗口标题 / OCR 命中，下面挂"同时段的录音" ——
  问"当时的录音"时，这就是答案。

**文字稿**点开是一篇独立的文章页：上面是播放器和时长/说话人/情绪/事件标签，
下面是识别出的原文（按句分段），左上角"← 返回总账"。活动声没有文字，
页面会明说"这段没有转写出文字"，播放器照样能听。

搜索范围：索引覆盖**最近 21 天**（`vsearch.py` 里的 `SEARCH_DAYS`），
再往前的日子仍能在时间轴里翻、明细里的链接也照样有效，只是不进搜索索引。
原因是索引要整个内联进页面（`file://` 下前端没法 fetch 本地 json），
不设限的话几个月后整页会变成几 MB。

日期和关键词都是**页面里的规则匹配**，不调模型 —— 双击打开就能用，
不依赖 Ollama 起没起。想调停用词或阈值，改 `vsearch_ui.py` 里的 `STOP`
和打分权重即可。

#### 屏幕大小变了？页面自己会跟着变

总账的排版不是死的。所有尺寸都乘一个 `--scale` 系数，由浏览器按**视口宽度**
（也就是 CSS 像素，跟 Windows 的显示缩放无关）自动选档：

| 视口宽度 | 缩放 | 内容区最大宽 | 正文 | 说明 |
|---|---|---|---|---|
| < 1920 | 1.0× | 940px | 12.5px | 普通屏，和以前一模一样 |
| 1920–2559 | 1.3× | 1220–1400px | 16.3px | 2K |
| ≥ 2560 | 1.6× | 1500–2100px | 20px | 4K（你现在的屏幕） |
| ≥ 2560 且 21:9 | 1.75× | 1650–2200px | 21.9px | 超宽屏，横向铺得更开 |
| 竖屏 / 宽高比 ≤ 1:1 | 1.15× | 1080px | 14.4px | 平板立着放 |

在 3840×2160 的 4K 屏上（系统缩放 100%）：内容区 1843px，占屏宽 48%，
正文每行 33 个中文字，天圆点直径 96px，日号 30px。

**缩放是等比的**：圆点到中轴 16px、点下的竖引线 16px、角标边线 16px 这些
对齐规矩全部乘同一个系数，所以放大后圆点不会被引线甩开、角标不会错位。

内容区宽度用 `clamp(最小值, 视口百分比, 最大值)`，所以**超宽屏上文字栏
还会随屏幕一起变宽**，不会在两侧留下一大片空白；但 2100px 封顶，避免
一行太长不好读。

要看页面在某个尺寸下的样子，把浏览器窗口拉宽/拉窄即可实时切换，
不用改任何配置。

### 5.10 网页是不是实时的

**采集一直是实时的，汇总曾经不是。** 这个区别很容易误会，说清楚：

| 环节 | 时效 |
|---|---|
| 录音、切段、转写、声纹 | 实时，说完几秒内入库 |
| 屏幕记录（Windrecorder） | 实时录，每小时挑一张小图留档 |
| 总账（那段话 + 时间轴） | 以前只在下次开机后补一次，**现在每 5 分钟一次** |

也就是说：你在 21:26 说的话，21:26 就已经在库里了；但"总账"这张给人的
答卷，旧版要等到下一次开机才写 —— 于是打开网页看到的是"上一次关机"为止，
自然会觉得"这不是实时的吗"。

现在由 `vlive.py` 每 5 分钟重算一次**当前这场开机**，替换总账里同一条，
并让网页自己刷新（页面顶部有一行 `● 正在记录　最后更新 21:32`）。
3 分钟不到就能在网页上看到刚才干了什么。

手动刷一轮（不用等）：

```powershell
.\.venv\Scripts\python.exe vdigest.py --live
```

几个设计上的取舍，先说明白，免得以为是 bug：

- **冻结的时段不重写**。上午那一段事实不会再变，文案走缓存直接复用；
  只有"当前正在长"的最后一段会重新问模型。所以一轮只要 6 秒左右，
  不是每次 9 段 × 6 秒那样把风扇吹起来。
- **那段总述半小时才重写一次**。它是"这次开机整体在干什么"，不是逐分钟
  流水；每 5 分钟重写会每次措辞都不一样，看着像在抖。
- **实时版扫文件只给 25 秒**（正式版 90 秒），来不及扫完的部分当场不显示。
  关机后下次开机补写的那一份是完整的、以它为准。
- **写不坏**：实时刷新和开机补写抢同一份总账，用文件锁排队；进程被杀锁
  自动释放，不会留下把后续总结永远堵死的标记文件。

### 5.11 只认中文：语种锁与模型选择

这台机器上只会出现普通话，但模型不知道，它会自己猜。实测旧数据里 72 条
转写有 **9 条**被标成韩语，内容是 `.그.`、`응.`、`我从买行네.` 这种噪声残字
—— 全是模型在短音频上瞎猜语种留下的。

**语种锁（已默认开启）**：`config.json` 里 `"asr_language": "zh"`。
SenseVoice 支持在解码前把语言钉死，钉住之后它不会再去猜。

实测 8 段真实录音（含抖音、外放新闻、自己说话）：

| 设置 | 判成非中文 |
|---|---|
| `auto`（旧） | 2 / 8 |
| `zh`（现在） | 0 / 8 |

钉死之后文字内容基本不变，短句会有个别出入 —— 那不是变差了，是换了一种
更偏向中文的猜测方式。要录外语素材，把 `asr_language` 改成 `"auto"` 再重启。

**噪声清洗**：即便钉死中文，1~2 秒的短段仍会产出「嗯。」「。」这类东西。
`voice_asr.scrub()` 会在入库前处理：抹掉假名/韩文，抹完不剩两个字就判为
噪声、文本留空。原始 `raw` 字段仍然保留，随时能回溯模型当时到底输出了什么。

**为什么不换纯中文 ASR 模型**：Paraformer-zh（阿里的中文专用模型）在
AISHELL-1 干净朗读集上确实更好（CER 1.95% vs SenseVoice 约 3.0%），但在
**带噪真实音频**上反而更差（同一套 184 条中文测试：SenseVoice 8.01%，
Paraformer 9.85%）。这台机器录的是外放新闻、抖音 BGM、隔着距离的家常话，
不是录音棚，所以留 SenseVoice —— 它还是唯一能顺带给出情绪和音频事件标签的。

**总结模型**：`config.json` 的 `"digest_model"`。默认已切到 `qwen3.5:9b`
（同参数量下中文表达明显比 gemma 自然；文件约 6.6GB，比原来的 7.8GB 还小）。
想换回来或换别的，改这一行即可，不用动代码。

## 七、常见问题

| 症状 | 原因 | 处理 |
|---|---|---|
| 进程数 0 | 守护进程本身没了 | 双击 `start_voice.vbs` |
| 进程数 3–5 | 某个子进程死了，守护进程正在退避重启 | 等 1–60 秒；连续失败会退避到 60 秒 |
| 时间线一条都没有 | 这段时间没检测到人说话，或全被噪声门丢了 | 跑 `--probe` 看麦克风；看 `recorder.log` 的"丢弃 N 段" |
| 屏幕状态显示"取自 X 分钟前的画面" | Windrecorder 批量写入滞后 | 正常现象，见下 |
| 屏幕库"未找到" | 跨月了，当月库还没生成 | 正常，录一段时间就有了 |
| 时间整体错 8 小时 | Windrecorder 的时间口径特殊 | 代码里已处理，若你自己写查询必须走 `to_wind()` |
| ASR 卡在 `download models from model hub` | 模型路径退回成了在线 id | 检查 `E:\AI\voice\models` 是否存在 |
| 日志里中文是乱码 | 子进程按控制台代码页输出，文件按 UTF-8 读 | 已修（`PYTHONIOENCODING=utf-8`），旧日志里的乱码改不掉，新的是干净的 |
| 总结里冒出 `config_src` 这种名字 | 模型在照抄文件系统 | 已修：喂给模型的输入里不含路径和代码名 |

**关于"屏幕状态滞后"**：Windrecorder 的 `record_seconds=300`，意思是每 5 分钟封一段视频再批量写库，所以屏幕记录天然比语音晚 1–2 分钟落库。不影响对齐（时间戳是对的），只影响"实时性"。想更实时可以把它改成 60，代价是视频碎片变多。

### 8.1 截图是怎么从 2.7 GB 变到 5 MB 的

先讲一件关键的事：**Windrecorder 每张截图都会顺手 OCR 一遍，文字存在它自己的库里**
（`video_text.ocr_text`）。实测 95 条记录**全都有文字**。也就是说——

> 分析"你在干什么"，从来就不需要那张图。图只是**认字的中间产物**。

所以做法是：文字留在库里当永久资产，图只当临时垃圾。

| 内容 | 留多久 | 一天大概多少 |
|---|---|---|
| 转写 / 声纹 / 总账 | **永久** | 几十 KB |
| 屏幕上的文字（在 Windrecorder 库里） | **永久** | 约 2 MB |
| **每小时一张压缩小图** | **永久** | **约 5 MB** |
| 原始录音 wav | 7 天 | 约 115 MB |
| Windrecorder 截图缓存（4K 原图） | **6 小时** | 从 2.7 GB 降到约 0.7 GB |
| 录像 | 30 天 | 几 MB |

**每小时那张小图**长这样：宽 2400px 的 JPEG，约 220 KB。挑的还是那一小时里
**屏幕上字最多**的一帧（字最多 = 信息最满 = 最能看出在干什么）。存在
`data\snapshots\2026-10-24\17-00.jpg`，总账里那个"17 点的屏幕"链接就指向它。

省多少：原来一天 2.7 GB，现在约 **5 MB**（小图）+ **0.7 GB**（6 小时内的原图）
≈ **降了 75%**；如果机器一天只开 6 小时，那连这 0.7 GB 都不会积。

### 8.2 三道安全阀（为什么不会删错）

删之前要过三关，缺一关就留着：

1. **文字已经认出来了才删** —— 查 Windrecorder 的库，确认这个时间点的截图
   已经被 OCR、文字已经落库。没落库就不删，否则这段屏幕活动会永久消失。
2. **那个小时已经有小图才删** —— 防止"图删了、代表帧又没存上"。
3. **最近 2 小时不动** —— 可能正在被录制进程写。

另有一个硬兜底：**超过 2 天无条件删**。因为万一 OCR 管线坏了，"文字没入库"
会变成永不删除的理由，磁盘又会被塞满。宁可丢图也不让磁盘爆。

### 8.3 手动跑

看一眼会删什么（**默认只看不删**）：

```powershell
.\.venv\Scripts\python.exe vclean.py
```

真删：

```powershell
.\.venv\Scripts\python.exe vclean.py --apply
```

改保留期（例：截图改成 3 小时）：

```powershell

```

单独补做小图（不动原图）：

```powershell

```

每次清理都记在 `data\logs\clean.log`，删了什么、回收多少可以事后查。
**只删文件，绝不动 `voice.db`** —— 删了音频，转写和声纹仍然完整。

### 8.4 屏幕文字的清洗与纠错

OCR 认出来的原始文字很脏：侧边栏的日期、图标被当成字、同一个词重复七八遍。
实测一条记录 1800 字，其中**只有 14% 是真内容**。

`vocr.py` 做四件事：

| 处理 | 例子 |
|---|---|
| 丢噪声行 | `隹荐` `釒资*斗` `5小时前` `10月8日` `918日` 全扔 |
| 繁转简 | `這`→`这`　`時`→`时`　`檔`→`档` |
| 修已知误识 | `隹荐`→`推荐`　`巳经`→`已经`　`磁盆`→`磁盘` |
| 去重复 | 同一条内容重复出现只留一次 |

**实测：173,878 字 → 24,502 字，压掉 85.9%，纠错 194 处。**

看效果：

```powershell
.\.venv\Scripts\python.exe vocr.py --days 1 --show
```

> ### 关于"自动纠错"，我把边界说清楚
>
> 我**只修有把握的**。比如"己经"改成"已经"是安全的——"己经"在中文里根本
> 不成词；但把"表格"改成"报表"就纯属瞎猜。
>
> 猜错了的代价比留着错字大得多：后面的分析全建在假文字上，而且你看不出来。
> 所以宁可留一个错字，也不制造一个假事实。
>
> 原始文字永远保留，清洗后的另存一份，两条都能对照。真想知道机器改了
> 我什么：`vocr.py --export` 会导出 raw 和 clean 两份 jsonl。

## 十一、版本号与自动更新（2026-10-25 新增，1.0.0 起）

### 11.1 版本号怎么来的

项目根目录一个纯文本文件 `VERSION`，里面就一行 `1.0.0`。
语义化三段：**修毛病**动第三位（1.0.1），**加功能**动第二位
（1.1.0），**大改版**动第一位（2.0.0）。打包时
`build_package.py --bump minor` 自动递增并写回文件，
同时把版本号、构建时间、更新说明（取自 `docs/CHANGELOG.md`
顶段）写进发布包的 `VERSION.json`。

本机版本身份证 = 安装根目录的 `VERSION.json`，总账网页顶部
常驻显示。它带一个 `state` 字段：`ok` = 好的，`testing` =
"文件已换入、冒烟未过"的中间态（只应存在几秒，见 11.4）。

### 11.2 更新源是什么

一个**放着完整发布包的目录**。可以是：

| 场景 | update_source 填什么 |
|---|---|
| U 盘更新（默认） | 安装包所在路径，插着 U 盘就能更新 |
| 局域网共享 | `\\NAS\share\VoiceGuard-1.1.0` 这种 UNC 路径 |
| 本机另一块盘 | `E:/releases/VoiceGuard-1.1.0` |
| 暂不更新 | 留空 |

### 11.3 分级增量：为什么发新版只要几秒

发布包的 `manifest.json` 把 payload 按 `code / models / python`
三个顶层目录分别记签名：

- `code`（约 700KB）：逐文件 sha256，**改一个字节都发现**；
- `models` / `python`（GB 级）：只按"路径+大小"清单算签名，
  纯 stat 不读内容，几千文件毫秒级（这两部分由构建脚本整体
  产出，没有人单独改里面某个文件）。

检查更新时哪部分的签名变了才传哪部分。日常发新版一般只动
`code`，从 U 盘拷 700KB，几秒完成；模型或依赖大版本才动
GB 级目录。更新完 `vupdate verify` 会拿本机文件逐个对清单
复检，保证换完整了。

### 11.4 四道安全闸（更新永远变不坏）

1. **暂存校验**：新版先整个拷进 `updates/staging-<版本>/`，
   按 manifest 校验通过才允许替换。拷一半的 U 盘在这一步就拦下。
2. **同盘原子换**：旧 parts 整体 rename 成 `updates/backup-<旧版本>-<时间>/`，
   staging rename 上位。同盘 rename 是秒级的元数据操作，不存在
   "换到一半"的窗口。data 目录从头到尾不碰。
3. **冒烟后承认**：换完先写 `VERSION.json(state=testing)`，
   跑冒烟测试（导入全部模块 + 用包里自带录音验证 ASR 真的能
   转出字）。失败 → 备份 rename 回来 + 状态还原，日志记一笔。
4. **断电自救**：`testing` 状态正常只存在几秒。守护进程每次
   启动先看这个状态，发现它说明上次更新中途死了，此时备份
   一定还在，**自动回滚再启动**。用户下次开机看到的还是旧版，
  录音链路一天都没断过。

### 11.5 日常操作

| 想干什么 | 做什么 |
|---|---|
| 更新到新版 | 双击桌面［检查更新］（或 `python vupdate.py apply`） |
| 看看有没有新版 | `python vupdate.py check`（开机自启也会定期查） |
| 当前版本 / 检查结果 | `python vupdate.py status` |
| 回退到上一个版本 | `python vupdate.py rollback` |
| 更新历史 | `python vupdate.py history` |
| 复检本机文件完整性 | `python vupdate.py verify` |
| 改更新方式 | config.json 的 `auto_update`：off / check（默认）/ auto |
| 改更新源 | config.json 的 `update_source` |

守护进程启动 1 分钟后自动 check 一次，之后每 24 小时。
`check` 模式只把结果写进 `data/update_state.json`，总账顶部
显示"有新版本 x.y.z"；`auto` 模式则派生独立进程执行更新并
让位（旧进程先退，新代码由更新器拉起，单实例锁不会打架）。

### 11.6 自己发一个新版

```text
# 1. 改完代码，跑全部测试
python test_update.py && python test_search.py

# 2. 升版本号并打包（--bump patch/minor/major）
python build_package.py --bump minor

# 3. 产物在 E:/AI/VoiceGuard-Package/releases/VoiceGuard-<版本>/
#    把这个目录拷到 U 盘 / 局域网共享，就是更新源
```

`--notes "修了搜索的日期过滤"` 可以覆盖默认更新说明
（不传则取 `docs/CHANGELOG.md` 顶段）。历史版本目录都留在
`releases/` 下，任何一个都能当回滚源。
