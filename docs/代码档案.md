## 二、进程拓扑

```
注册表 Run 键（HKCU\Software\Microsoft\Windows\CurrentVersion\Run）
├─ VoiceRecorder     → pythonw voice_daemon.py
│                       ├─ pythonw voice_recorder.py   ← + venv shim
│                       ├─ pythonw voice_asr.py        ← + venv shim
│                       └─ pythonw vsnap.py --loop     ← + venv shim
├─ VoiceBootTasks    → pythonw boot_tasks.py（等 90s → 等模型 → vdigest --prev → vclean --apply）
└─ Ollama            → "ollama app.exe"

WorkBuddy 自带的（不归本项目管）
└─ WorkBuddy.WorkBuddy → WorkBuddy.exe
```

实际 `pythonw` 进程数是 **8**（每个逻辑进程带一层 venv 的启动器）。

**为什么 vsnap 要常驻而不是"清理时顺手做"**：截图原图 6 小时后就删了。
如果只在清理那一刻才去挑代表帧，中间如果进程没跑、索引丢了、机器休眠过，
那个小时的代表帧就**永远补不上了**（原图没了）。常驻进程每 5 分钟扫一次，
还自带自愈：实测手动删掉 index.json 里的记录，5 分钟内它自己补了回来。

**为什么 WorkBuddy 不写进我们的清单**：它自己早就注册了 `WorkBuddy.WorkBuddy`。
再写一条会启动两个实例，第一版就犯了这个错，`install_autostart.py` 里
`LEGACY` 项会在安装时把它清掉。

**为什么不建 .lnk**：`WScript.Shell` 这个 COM 组件在本机安全策略里被拦，
建不了快捷方式。注册表 Run 键是同等合法的自启位置，且任务管理器里可见可禁用。
`install_autostart.py` 负责装/看/卸。

**为什么不加 `schtasks` 计划任务**：`schtasks.exe` 也在安全策略黑名单里。
Run 键不需要提权，正好够用。

**守护策略**（`voice_daemon.py`）：
- **单实例锁**：`data/daemon.lock` 存 pid，每 2 秒 `touch()` 当心跳；
  启动时"心跳 <300 秒 **且** 那个 pid 确实是 python"才认为已有实例在跑。
  两个条件缺一不可 —— 只看 pid 挡不住 PID 复用（会把无关进程当成自己人，
  于是静默不启动，录音断了都没人知道）；只看文件时间挡不住僵死。
  查进程名用 `QueryFullProcessImageNameW`，查不到就当作"不是我们的"。
- 每 2 秒巡检一次子进程
- 稳定运行过（>20s）后崩溃 → 1 秒后立刻重启
- 启动 20 秒内就崩溃 → 指数退避 `2^n` 秒，上限 60 秒，并记 `ERROR` 日志
- 退出时先写 STOP 文件让子进程自己收尾，最多等 15 秒，超时才 `kill`
- 子进程启动时注入 `PYTHONIOENCODING=utf-8`（见坑 #11）

**为什么不用 Windows 服务**：服务跑在 Session 0，**访问不到麦克风/摄像头**（Windows 的会话隔离）。必须用"用户登录时触发"的自启方式。

## 三、一次说话走了哪些地方

```
① PortAudio 回调线程（独立线程，绝对不能碰 SQLite）
   48000Hz / 1ch / int16 / 每块 1440 样本（30ms）
   → decimate3()  3:1 抽取 + FIR 抗混叠 → 16000Hz / 480 样本
   → queue.put_nowait((480样本, time.time()))
   ↓ 到此为止，回调只做这两件事

② 主线程（voice_recorder.run 的 while 循环）
   q.get(timeout=0.5) → Segmenter.feed(frame, ts)
        │
        ├ 未激活：进 pre_roll（300ms 环形缓冲）
        │    VAD 连续 90ms 为语音 → 激活，把 pre_roll 一并写入（保住首字）
        │
        └ 已激活：
             · 帧写入 .pcm（buffering=0，无缓冲，随写随落盘）
             · 每 1 秒 touch_segment() 心跳（崩溃后知道录到哪）
             · 连续静音 720ms → 收尾
             · 或累计 30 秒 → 强制收尾（长句切段）

③ Segmenter._end()  ← 噪声门在这里
   计算段内语音帧占比 voiced/len(frames)
   < 0.65  → drop_segment()，连 wav 都不生成，直接删 .pcm
   ≥ 0.65  → finalize_pcm() 封 WAV + close_segment() 写库

④ voice_asr.worker（另一个进程，轮询）
   pending_asr() 取 state='closed' 且 asr 表无记录的段
   → Transcriber.run()      SenseVoice 推理，拿到 text/情绪/事件/原始标签
   → parse_rich()           从 <|HAPPY|> 这类标签里拆出情绪和事件
   → rich_transcription_postprocess()  擦掉标签得到干净文本
   → save_asr()
   → SpeakerEncoder.embed() 192 维声纹向量
   → classify()             与档案质心比余弦
   → speaker 表落库（连嵌入一起存）

⑤ voice_timeline（按需运行，不常驻）
   merged() 查 voice.db  →  对每句调 WindReader.screens_during()
   打印
```

## 五之补、会话摘要流水线（vsession / vcollect / vdigest）

### 为什么以"会话"为单位而不是"天"

这台机器的用法是**为了某个任务开机、做完就关**，不是每天定点开机。
实测事件日志里的会话长度：1.4 小时、3.7 小时、10 小时都有，还有大量"0 小时"其实是重启。
**按天定时生成摘要可能永远不触发**，所以边界必须由 `6005/6006` 事件决定。

三个触发点（都不依赖时钟）：
1. 开机时 —— 若上一次会话还没总结，补生成（数据已完整）
2. 空闲 —— 可以对当前会话做一次草稿
3. 手动 —— 用户开口时

### 数据流

```
vsession.sessions()      事件日志 → [(开机, 关机, 是否正常关机)]
        ↓
vcollect.file_changes   scandir + 扩展名白名单 → 文件清单（含 peek_file 正文片段）
vcollect.screen_activity Windrecorder video_text → 按应用聚合的活动段
vcollect.voice_lines    voice.db → 同人连续说话合并
vcollect.print_events   PrintService 日志 → 打印记录
        ↓
vdigest._brief()        压成 ~2400 token 的事实清单（编号 | 时间 | 内容片段）
        ↓
    ┌───────────────┴────────────────┐
--brief（默认）                  --llm（可选）
交给外部模型写稿                本地 gemma4-12b 写
        ↓                               ↓
vdigest.render()  用真实数据填文件名/时间/大小，模型只提供"归组 + 说人话"
```

### 三个关键设计

**1. 模型不参与"事实"**
文件名、时间、大小、路径全部由 `render()` 从真实数据填。模型只输出
`{"headline":..., "tasks":[{"title","what","artifacts":[编号],"screens":[编号]}]}`，
`artifacts`/`screens` 只能是清单里的整数编号。`sanitize()` 会把越界编号直接丢掉——**不补、不猜**。
这样模型再离谱也编不出一个不存在的文件名。

**2. 叙述默认不由本地模型写**
本机 gemma4-12b（Q4_K_M，7.4 GB）实测约 **34 tok/s**，写一份摘要要几分钟，
加 `format:"json"` 还会更慢（曾出现 >420 秒超时）。而这份活只需要"把编号归组、写两句话"，
用 12B 是浪费。默认走 `--brief`：后台只产事实清单，叙述交给 WorkBuddy 的在线模型（在对话里写）。
`--llm` 保留作为无人值守时的兜底，但**不要放在关键路径上**。

**3. 文档正文靠 zip 直读，不装 python-docx**
docx/xlsx/pptx 本质是 zip+XML。`peek_file()` 直接读
`word/document.xml` / `ppt/slides/slideN.xml` / `xl/sharedStrings.xml` 再剥标签，
零依赖拿到"这份文档里写了什么"。失败一律返回空串，不影响主流程。

### 性能实测（重要）

| 做法 | 扫描 10 万文件耗时 |
|---|---|
| `os.walk` + `os.stat`（第一版） | **119 秒** |
| `os.scandir` + `entry.stat()` + 扩展名白名单 + 目录剪枝 | **0.3 秒** |

差 400 倍。关键是**先用扩展名过滤再 stat**——白名单外的文件根本不进统计。

## 五、时间口径（红线，改错必然整体错 8 小时）

这是整个项目**最容易出错、也最难发现**的地方。

| 数据源 | 字段 | 含义 |
|---|---|---|
| `voice.db` | `segment.start_ts` / `end_ts` | **真实 UTC epoch**（`time.time()`），float，含毫秒 |
| Windrecorder | `video_text.videofile_time` | **`calendar.timegm(time.localtime(ts))`** —— 把本地墙钟当成 UTC 编码，比真 UTC 多 **28800 秒** |

换算只有两个函数，**任何跨库比较都必须过它们**：

```python
def to_wind(ts):   return calendar.timegm(time.localtime(ts))   # 真UTC → Wind口径
def from_wind(wt): return time.mktime(time.gmtime(wt))           # Wind口径 → 真UTC
```

实测校验：本地 `16:48:39` 的记录，库里存的是 `1792860519`，该数值按 UTC 解释正好是 16:48:39。

**另一个坑**：`video_text` 表**没有** `datetime_str_record` 字段（早前以为有，是错的）。能用的只有 `videofile_time`、`win_title`、`ocr_text`。

## 六、数据模型

### 6.1 voice.db 四张表

```sql
segment                                  -- 一段语音
  id            INTEGER PK
  start_ts      REAL      -- 真实 UTC epoch（由样本数反推，见下）
  end_ts        REAL      -- 帧时间戳
  duration      REAL      -- end_ts - start_ts
  sample_rate   INTEGER   -- 恒 16000
  samples       INTEGER   -- 样本数，权威值
  rms           REAL      -- 段内均方根
  peak          INTEGER   -- 峰值
  wav_path      TEXT      -- 绝对路径
  state         TEXT      -- 'open' | 'closed'
  created_at / updated_at REAL

asr                                      -- 一段的转写（1:1）
  segment_id    INTEGER PK
  text          TEXT      -- 干净文本（标签已擦除）
  lang          TEXT      -- zh/en/yue/ja/ko
  emotion       TEXT      -- NEUTRAL/HAPPY/SAD/ANGRY/FEARFUL/DISGUSTED/SURPRISED
  events        TEXT      -- JSON 数组，如 ["Speech","Laughter"]
  raw           TEXT      -- SenseVoice 原始输出（带 <|HAPPY|> 标签），排错用
  model / rtf / created_at

speaker                                  -- 一段的声纹（1:1）
  segment_id    INTEGER PK
  label         TEXT      -- 档案名 | '其他' | '?'
  score         REAL      -- 与最佳档案的余弦
  emb           BLOB      -- 192 个 float32 = 768 字节
  dim           INTEGER
  created_at

meta                                     -- 键值杂项
  k TEXT PK, v TEXT
```

**嵌入必须落库**这条是刻意设计的：改阈值、加档案时只要 `--relabel` 重算标签，**不用重跑模型**。整库重判 12 段约 0.1 秒，重跑模型要 30 秒以上。

### 6.2 硬不变量：duration 必须由样本数反推

```python
end_ts   = self.last_ts                    # 墙钟只提供终点
start_ts = end_ts - n / float(self.sr)     # n = 样本数
```

**为什么**：音频长度由样本数唯一确定，而墙钟会抖动、队列会延迟。早前用 `end_ts - start_ts` 直接算，出现过"19200 样本却记 0.48 秒"和"差 720ms"两种分叉。

同理 `recover()` 里也是从文件大小反推：`n = (wav.stat().st_size - 44) // 2`。

### 6.3 Windrecorder 的表（只读）

```sql
video_text
  videofile_time   INTEGER   -- 特殊口径，见第五章
  win_title        TEXT      -- 格式 "窗口标题 | 进程名"
  ocr_text         TEXT      -- 屏幕上的文字（OCR 结果）
```

`app_of(title)` 取 `|` 后面那段当进程名做归类。

## 七、踩过的坑（按掉坑代价排序）

### 1. 麦克风在共享模式下完全静音（代价最大）
微软的 `Voice Clarity` APO 挂在麦克风端点上，把所有 WASAPI 共享模式采集变成全零。表现为峰值只有 2–3。
**这个 bug 影响全机**：微信语音、腾讯会议、豆包、语音输入法收到的都是无声。
修复键：`HKLM\...\MMDevices\Audio\Capture\{14b7c662-...}\FxProperties`
`{1da5d803-d492-4edd-8c23-e0c0ffee7f0e},5` = DWORD `1`，然后重启 `audiosrv`。
备份在 `E:\AI\voice\backup\mic_fxproperties_before.txt`。

> 写这个键时踩到二层坑：`New-ItemProperty` 和 `OpenSubKey($true)` 会顺带申请 `KEY_CREATE_SUB_KEY`，而该键对 Administrators 拒绝这个权限。**唯一可行路径是 Python `winreg.OpenKey(..., KEY_SET_VALUE)` + `SetValueEx`**。

### 2. Windrecorder 的帧极其稀疏，且行语义不是"瞬间"
实测帧间隔约 **2 分 13 秒**（只在画面变化时落库），批量写入滞后约 2 分钟。
关键认知：**一行代表"从这一时刻起到下一行为止"的屏幕状态**。
所以匹配一句 4 秒的语音，不能做区间求交（大概率落空），必须**带上 t0 之前的最后一行**（状态延续）。这就是 `screens_during()` 里那个 `base` 查询存在的全部理由。

### 3. `rich_transcription_postprocess` 会擦掉情绪标签
SenseVoice 的输出形如 `<|zh|><|HAPPY|><|Speech|>今天天气不错`。
`rich_transcription_postprocess()` 把尖括号标签**全部删掉**再拼接，只留纯文本。
如果先 postprocess 再解析，情绪和事件全丢且不可恢复。
**必须先从 `raw` 里正则抽标签，再 postprocess。**

### 4. SQLite 连接不能跨线程
PortAudio 回调在独立线程。早期在回调里调 `voice_db.open_segment()`，直接抛
`ProgrammingError: SQLite objects created in a thread can only be used in that same thread`。
现在的分工：**回调只做抽取 + 入队**，VAD/文件/数据库全在主线程。

### 5. 传 model id 给 FunASR 会联网卡死
`AutoModel(model="iic/SenseVoiceSmall")` 每次启动都向 modelscope 解析最新版本，日志停在
`download models from model hub: ms` 两分钟以上。
必须传**本地目录**（`vcfg.model_dir()`）。加载时间从 3.5s 降到 1.8s。
同理还要设 `MODELSCOPE_CACHE` 到 E 盘，否则 `C:\Users\...\.cache\modelscope` 会重复存一份 940MB。

### 6. pythonw 下 `sys.stdout` 是 `None`
`logging.StreamHandler(sys.stdout)` 会让每条日志都抛异常。
`vcfg.setup_logging()` 里判断 `if sys.stdout is not None` 才挂控制台 handler，永远挂文件 handler。

### 7. pythonw 下停止不能用信号
没有控制台，`GenerateConsoleCtrlEvent` 送不进去；`TerminateProcess` 又跳过 SIGTERM。
**统一用 `data/STOP` 文件**作停止约定。守护进程退出时还会重写这个文件，新实例启动时自动清掉。

### 8. 合成音之间相似度奇高
Huihui 与 Zira 都是微软 SAPI 引擎，彼此相似度 0.49–0.53；而真人同人跨次只有 0.69、不同人是 −0.08。
如果用 0.45 当阈值，Zira 会被判成 Huihui。**阈值必须是 0.55。**
另一个细节：Zira 段与 Huihui 段的**单对**相似度到过 0.57（已越阈值），但走**质心**只有 0.53，被正确挡下。**永远比质心，不要比两两。**

### 9. 分块取样会把停顿块当样本
登记时把长段切成 3 秒块，盲切会把中间的换气/停顿也切成块。实测一段 15.8 秒切 7 块，其中 2 块是停顿，与真人质心相似度只有 0.46/0.26，把簇内最低相似度拉到 0.331。
修复：`_voiced_ratio()` 按 30ms 帧算语音占比，`< spk_chunk_min_voiced` 的块在取嵌入前丢弃；筛完不足 3 块则退回全部（宁可留脏也不能让登记失败）。

### 10. `config.json` 会整体覆盖 `vcfg.DEFAULTS`
改了 `vcfg.py` 里的默认值但没改 `config.json`，**等于没改**。
改参数的顺序：先改 `DEFAULTS`，再改 `config.json`，最后 `vcfg.load()` 打印确认。

### 11. 思考型模型不关 `think` 会"跑满还不给答案"（本次最贵的一处）

现象：`gemma4-12b-unc` 一次摘要跑 **420 秒以上**超时，返回的 `content` 是空字符串，
`eval_count` 却有几百。看着像"模型太慢/机器不行"。

真相：Gemma 4 是**思考型模型**，思考内容走 `message.thinking` 字段，
思考没结束 `message.content` 一直是 `""`。当时又要求它输出 `format:"json"`，
等于让它一边长篇思考一边逐字数括号，自然永远跑不完。

```python
# 错：content 永远是空的，直到 think 结束（而 think 可能吃掉整个 num_predict）
payload = {"model": MODEL, "format": "json", ...}
txt = d["message"]["content"]          # ""

# 对：关掉思考，只让它写结果
payload = {"model": MODEL, "think": False,
           "options": {"num_predict": 400, "num_ctx": 3072}}
```

同一件事：**420 秒 → 4 秒**。

配套的三条设计（都在 `vdigest.py`）：
1. **输出从 JSON 改成散文**：交付物本来就是"一段话"，让模型写 200 字比让它
   构造 6 个任务对象快一个数量级。
2. **`num_predict` 硬顶 400**，跑到 400 就截断，防止跑飞。
3. **老版本 Ollama 不认 `think` 会返回 400** → `_post_chat()` 检测到 400/422
   就去掉这个键重发一次。

### 12. 子进程日志中文乱码

`voice_daemon.py` 用 `open(..., encoding="utf-8")` 接子进程的 stdout，
但子进程默认按**控制台代码页（GBK）**编码输出，落盘就成了 `�豸 idx=18`。
修法：spawn 时注入 `PYTHONIOENCODING=utf-8` + `PYTHONUTF8=1`。

### 13. 一直以为"截图是资产"，其实它是垃圾（省了 2.7 GB/天）

最早的清理策略是"截图留 1 天"，因为默认认为**图比文字重要**。
后来查 Windrecorder 的库才发现：

```
video_text 总行数        : 91
其中 OCR 文字 >20 字符    : 91      ← 100% 都有
对应 PNG 文件还在磁盘上的 : 81
```

**它每张图都 OCR 过了，文字全在库里。** 而且 `is_picturefile_exist` 大多是 0
—— Windrecorder 自己也认为图是合成完视频就能扔的临时文件。

所以图对"总结"的贡献是零，真正该永久保留的是：

| 资产 | 在哪 | 多大 |
|---|---|---|
| 屏幕文字 | Windrecorder 的 `video_text.ocr_text` | 一天约 2 MB |
| 每小时代表帧 | `data/snapshots/` | 一天约 5 MB |
| 截图原图 | `cache_screenshot/` | **一天 2.7 GB** ← 唯一该删的 |

改完之后：保留期 1 天 → 6 小时，删之前先存代表帧，实测一次回收 1.22 GB
（2.67 GB → 1.45 GB）。**教训：动手优化之前，先确认那个东西到底有没有人用。**

### 14. 删图的三道锁，以及"为什么必须有个硬兜底"

只加"删前检查 OCR 已入库"是不够的 —— 万一 OCR 管线坏了（模型目录被挪、
依赖升级失败），"文字没入库"会变成**永不删除**的理由，磁盘照样被塞满，
而且用户完全不会察觉。所以定了三道锁 + 一个兜底：

```
文字已入库   ← 缺了它，屏幕活动会永久消失
该小时有代表帧 ← 缺了它，图删了画面就彻底没了
最近 2 小时不动 ← 防抢文件
────────────────────────────────────
超过 2 天无条件删 ← 防止上面三条把磁盘锁死
```

实测验证：手动删掉 `snapshots/index.json` 里某个小时的记录，清理器立刻
"另有 12 个目录因为所属小时还没存代表图，先留着"。而常驻的 vsnap 在
5 分钟内把索引补了回来 —— 两套机制互相兜底。

### 15. 总账里同一次开机会出现两条

一条说"至今仍在用"（会话进行中生成），一条说"18:40 结束"（下次开机补写）。
用户看着像 bug。修法：`append_ledger()` 从标题里抠出开机时间当 key，
同 key 直接替换而不是追加，返回 True 表示是替换。

### 16. 把家里人当成了手机（离座判定的一次误判）

用户要求"等任务时刷手机的时间不要细记，一句话带过"。第一版判定是：

```python
media = density >= 0.12 and (non_self > 0.5 or bgm or hints)   # ← 错
```

`non_self`（声纹不是本人）单独就能触发 —— 结果**家里人在客厅聊天**
会被判成"你在刷抖音"。因为说话本来就不是本人。这个错很难看：把家里人当成了手机。

改成必须有一个**媒体专有**的特征：

```python
strong = bgm or bool(hints)                 # BGM 事件 / 短视频的词
weak   = non_self >= 0.9 and density >= 0.45  # 连续几十分钟没人应答地"说"
media  = strong or weak
```

并且结论分三档，证据到哪说到哪：

| 证据 | 措辞 |
|---|---|
| BGM 或抖音快手这类词 | "像是在抖音上刷——猜是在用手机打发等待时间" |
| 声纹是别的具体的人 | "声纹显示是屋里的另一个人在说话，没记具体内容" |
| 什么都判不出 | "有声音，分不清是家里人在说话还是在放东西，因此没有细记" |

另两个必要的保守设计：
- **屏幕活动覆盖不到 10 分钟就不判** —— 录屏刚起时的"空档"是没数据，不是没人动电脑
- **完全没声音不算离座** —— 人可能是出去了，这不是走神

五个场景都写了受控测试（证据齐全 / 声音太少 / 家人说话 / 数据不足 / 完全无声），
全部通过后才接进主流程。

### 17. 模型会把"在刷手机"简化成"离开了座位"

即使 brief 里明说了"像是在抖音上刷"，模型仍倾向于写成"期间有一段时间你离开了座位"，
把信息量最大的那半句吃掉了。修法是把要求说得更硬：

> 必须点明那会儿是在用手机/放视频这类，不能简化成「离开了座位」——
> 那句话的意义就是记下「我走神了」。

改完后两次测试分别写出"你可能在用手机等事情处理"和"似乎在用手机刷内容，
没在操作电脑"。同时保留程序兜底：模型没写到（用 `_said_drift()` 查关键词），
`render_ledger()` 就把 `drift_sentence()` 补进去 —— **这一段不能因为模型今天话少就丢了**。

### 18. 门槛只按"近讲"校准，把外放的声音全丢了（最贵的一次）

2026-10-24 18:40-18:47，用户在看一段讲越南的新闻（标准普通话），
事后问"识别出来了吗"——答案是**一个字都没有，连音频都被删了**。

根因不是模型不支持，也不是麦克风坏了，就是一道数字：

```python
bad = ratio < cfg["min_voiced_ratio"]        # 0.65
```

`min_voiced_ratio=0.65` 当初是拿"本人近讲"校准的（实测真语音 0.74-0.85）。
但**从扬声器回放的声音是远场**，人声要穿过距离和外放，VAD 占比天然低一截：

| 音频 | 语音帧占比 | 过 0.65 门槛 | 结果 |
|---|---|---|---|
| 本人近讲 #417 | 0.72 | 通过 | 存盘 |
| 抖音 BGM #444 | 0.78 | 通过 | 存盘 |
| **新闻回放** | **0.49** | **不通过** | **整段删掉** |

那一轮 recorder 的退场日志写着 `共落盘 5 段，丢弃 211 段`——
7 分钟的新闻全在那 211 里，pcm 被 `unlink()` 得干干净净，**事后无法挽救**。

排查时走过的三条死路（记下来省得再走）：

1. 以为是越南语不支持 —— SenseVoice 确实只有 zh/en/yue/ja/ko，
   但**用同一段音频手动跑，它是能出字的**（`全是在完成补完规则。`），说明模型够用。
2. 以为是抽取滤波削了高频 —— 实测 `_DECIM` 的 -3dB 在 10.9kHz，
   把 48k 原始音频过一遍 `decimate3`，输出频谱和输入一模一样。
3. 以为是 WASAPI 的 APO（Voice Clarity）在降噪 —— 同一台设备四个端点，
   WASAPI 和 MME 录的底噪频谱完全一致（1k 以上都是 -25dB）。

**真正的证据只有一条**：把逐帧 VAD 判决打出来，`#444` 抖音 78%、`#417` 说话 72%、
新闻 49%。49 < 65，就是它。

修法是加第二道门 —— 不再只认"清楚"，也认"够响够长"：

```python
strict = ratio >= 0.65                                    # 近讲、清楚
loud   = (时长 >= 1.5s and rms >= 1000 and ratio >= 0.30)  # 外放、远场
bad    = 太短 or not (strict or loud)
```

`rms >= 1000` 是关键闸：这颗麦的底噪 RMS≈90-110，键盘碰麦约 400，
新闻回放 2672，本人说话 866-1085。噪声根本到不了 1000。
日志里会打 `[严]` / `[放宽]` 标记，一眼能看出这段走的哪道门。

回归验证 10 个场景（含 5 个真实实测值 + 5 个构造的噪声/瞬间响声）全过：
新闻保留、说话保留、BGM 保留，键盘/风扇/瞬时咔哒/无人声音乐全部丢弃。
端到端也验了：外放播一段 14 秒中文，落盘 `#615 15.06s rms=2045 语音占比=0.82 [严]`，
转写正常产出。

**教训**：任何按"占比""密度"设的阈值，只要校准样本是单一场景（近讲），
就一定会误杀另一个场景（外放）。设阈值时要问一句"这个数在别的场景下是多少"。

**事后实证（同一天 19:03 复测同一段新闻）**：

| 段 | 时长 | 语音占比 | 走哪道门 | 旧门槛 0.65 |
|---|---|---|---|---|
| #669 | 24.6s | **0.47** | 放宽 | **必丢** |
| #670 | 30.0s | **0.56** | 放宽 | **必丢** |
| #671 | 29.3s | 0.68 | 严 | 保留 |

同一条新闻，第一次放占比 69%，第二次 47% / 56% —— **同一个音频源的占比
会随音量、距离、房间反射大幅波动**。这是"单一固定门槛不可靠"最直接的证据。

### 19. 删文件的异常会把整个录音器带走（连崩 7 次）

`finalize_pcm()` 生成 wav 之后 `pcm.unlink()`。这一句在受限环境下会抛异常
（本机表现为安全策略拦截），异常一路冒泡把进程打死。守护进程拉起 → 又崩 →
退避 1/2/4/8/16/30 秒 → 18:58:54 到 19:02:16 整整 3 分 20 秒的录音全丢。

日志里的指纹长这样，看到就知道是这一类：

```
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] targets:["...185832_916.pcm"]
===== 2026-10-24 18:59:02 start =====     ← 紧接着就重启
```

修法：`_safe_unlink()` 把删除包起来，失败只 `log.warning`。

> **原则：清理动作永远不能是致命路径。** 删不掉最多多占几 MB（`vclean` 会兜底），
> 崩了就是丢录音 —— 这两件事的量级差了几个数量级。

同一次事故还暴露出另一个坑：`max_segment_s` 的强制切段写在 `feed()` 里，
**要求"还有帧进来"才会执行**。一旦音频流静默（设备被抢、驱动挂起），帧永远不来，
段就永久 `state=open`、`duration` 不涨，后续录音也不再落盘。
修法是加 `Segmenter.reap()` 看门狗：`now - last_ts > max_segment_s + 5` 就强制收尾。

### 20. 进行时写的摘要会挡掉关机后的补写

`vdigest` 在会话还在进行时也会写一条总账（显示"现在 结束"），并调
`mark_digested()` 打标记。问题出在 `unresolved()` 只判断"有没有标记"：

```
done = _digested_boots()          # 只看 boot 在不在集合里
if s["boot"] in done: continue    # 有标记就跳过
```

于是关机重启后，`boot_tasks` 认为"上次已总结过"，直接跳过 ——
**18:03 之后到 20:47 关机之间的内容永远补不上**，总账里那条一直停在半成品。

根因是索引里那条 `"shutdown": null`：它记录的关机时间是空，说明写的时候
会话还没结束。修法是把它判为"半成品"：

```python
def _stale_boots() -> set[float]:
    return {round(float(x["boot"]), 0)
            for x in _load_index() if x.get("shutdown") is None}

if s["boot"] in done and s["boot"] not in stale:
    continue          # 只有"完整标记"才算总结过
```

顺带的收获：`mark_digested` 只在 `sess["shutdown"] is not None` 时调用这个判断
本来就写对了，缺陷完全在读取端 —— **写入端和读取端对"已完成"的定义必须一致**，
这里是"有记录" vs "记录已完整"。

修完当天实测：08:42 那次会话从 9 小时 46 分（半成品）补成了 12 小时 4 分。

### 21. 时间轴的 HTML 别每个节点都开一个 `<ol>`

总账要"竖向时间轴"，`###` 小节在 md 里是独立段落，很容易顺手写成：

```python
if t.startswith("### "):
    close_tl(); out.append('<ol class="tl">')   # 错：每个节点一个 ol
```

结果每个 `<li>` 都是单独一条时间轴，`ol.tl::before` 画的那根竖线一段一段断开。
正确做法是连续的 `###` 共用一个 `<ol>`，只在遇到新的 `##` / 链接 / `---` 时才关。
同理"想看细节"的链接必须先 `close_tl()` 再输出，否则会被塞进最后一个 `<li>` 里。

另一个坑：屏幕 OCR 认出的文件名不能直接进正文。实测把"使用手册"读成
"创建用手册""已读取用手册"，还混进过 `python -m venv` 这种命令行残片。
`_canon_docs()` 的做法是拿它跟这次**真实动过的文件名**比相似度（difflib ≥ 0.6
就用真名），差太远且过长的一律丢掉 —— 宁可少写一个，不写错的。

### 22. "监控是实时的吗" —— 采集实时，汇总不是（用户第一次打开网页就会问）

2026-10-24 21:29 用户问："这个监控不是实时的么？那为什么没有出现现在 21:26 的监控内容。"

先查了事实，结论是两条，别混为一谈：

| 环节 | 真实时效 |
|---|---|
| 录音 / 切段 / 转写 / 声纹 | 真的实时（21:28:31 的通话内容，21:28:31 就入库了） |
| Windrecorder 屏幕记录 | 真的实时（原始帧逐秒写，只是每小时挑一张小图留档） |
| 总账（`总账.html`） | **不是**。只在"下一次开机后 90 秒"为上一次会话生成一次 |

所以那次的现象是：机器 20:48 重启过，总账里已经有一条 `08:42 开机 · 20:47 结束`；
而 20:48 这场正在用，从头到尾没有任何条目 —— 因为按设计它"还没结束"。
用户看到的"没有 21:26 的内容"不是漏采，是**汇总层的设计本来就不覆盖进行中的会话**。

修法：`vdigest.py --live` + `vlive.py` 每 5 分钟一轮，把当前这场重算到此刻。
三个必须做的配套，少一个就会变成新的坑：

1. **节点文案必须缓存**（`data/node_cache.json`，键 = 开机秒 + 起 + 止）。
   不缓存的话 9 个节点要调 9 次模型 ≈ 1 分钟，每 5 分钟来一次，风扇一直响。
   实测加缓存后一轮 6 秒（只有正在长的最后一段重算）。
   注意：**只缓存模型真写出来的**。模型掉线时兜底的干巴句子一旦进缓存，
   那段话就被永久钉死了。
2. **总述半小时才重写**（`data/live_para.json`）。那段话是"这次开机整体
   在干什么"，不是逐分钟流水；每轮都重写会导致措辞每次都变，看着像在抖。
3. **写总账要排队**（`data/digest.lock`，`msvcrt.locking`）。开机补写和实时
   刷新会同时改同一份文件。用文件锁而不是"存在即锁"的标记文件 —— 进程被
   强杀时系统会自动释放锁，标记文件会留下来把后续所有总结永久堵死。

另外两个容易忽略的细节：

- 实时模式扫文件只给 25 秒（正式 90 秒），扫不完当场就不显示，页面会少几个
  文件名。**关机后补写的那一份才是完整的**，以它为准。
- `vlive.py` 启动时如果看到 `data/STOP` 不要立刻退出：它和守护进程同一秒
  被拉起时，STOP 还没被守护进程清掉（清 STOP 的代码在单实例检查之后）。

### 23. 全中文环境却在输出韩文：语种别让它猜，模型也分"为谁而生"

2026-10-24 用户提出："我在中国，录音全是中文，避免识别出韩语日语，能不能换中文模型。"

先查数据：72 条历史转写里有 **9 条**语言标签是 `ko`，内容是 `.그.`、`응.`、
`我从买行네.` 这种 1~2 秒噪声段。不是"模型不支持中文"，是**短音频上语种
判别本来就不可靠** —— 一秒的沙发响动，猜中文还是猜韩文对模型来说概率差不多。

两件事分开处理：

**（1）ASR 侧：钉死语言 + 清洗，不换模型。**

`SenseVoice.generate(language="zh")` 能在解码前把语言固定住。实测 8 段真实
录音（抖音、外放新闻、自己说话）：`auto` 判成非中文 2/8，`zh` 是 0/8，
文字内容基本不变。再加一道 `voice_asr.scrub()`：抹掉假名/韩文，抹完不剩
两个字就判噪声、文本留空（原始 `raw` 保留可回溯）。

**为什么不换 Paraformer-zh**（这是本次调研最反直觉的结论）：它在 AISHELL-1
干净朗读集上确实更好（CER 1.95% vs SenseVoice ~3.0%），但在**带噪真实音频**
上反而更差 —— 同一套 184 条中文测试，SenseVoice 8.01% vs Paraformer 9.85%。
厨房里的外放新闻不是录音棚。而且 Paraformer 给不出情绪和音频事件标签。

**（2）总结侧：换模型，这才是真正的短板。**

`gemma4-12b` 是英文优先的模型，中文能写但带翻译腔，实测输出会是
"运行对话环境程序""处理产品相关文档"这种半生不熟的措辞，还会自作聪明
给出"选项一/选项二"。换 `qwen3.5:9b` 后同一段事实的输出：

> 下午我在 WorkBuddy 里改语音链路的手册时，正好外放了一段越南海牙认证公约的新闻。

速度也变了：同一段提示词，gemma 8.0 tok/s / 22.4s，qwen3.5:9b **47.1 tok/s / 11.8s**。
文件还更小（6.55GB vs 7.38GB），10GB 显存放得下。

代码上只加了 `digest_model` 这一个配置键（`MODEL = vcfg.load().get(...)`），
换模型不用改代码。⚠️ 换完必须清 `data/node_cache.json`，否则节点文案会全部
命中旧缓存，看不出区别 —— 这个坑第一次换模型时踩了个正着。

顺带一个措辞坑：`_voice_kind()` 原来对未知声纹返回"分不清是谁"，模型会原样
抄进正文，读起来像病句（"音响里一直放着声音分不清是谁在说话"）。改成
"说话人未识别"这种标签式说法，模型就不会把它当句子用。

### 24. 页面刷新偏偏撞在写文件的那一刻，于是"丢了一小时"

`write_text()` 是**先清空、再写**。页面的 `meta refresh` 间隔和后台重算间隔
都是 300 秒，两者相位几乎固定 —— 刷新请求正好落在写盘的那几十毫秒里，浏览器
读到一份被截断的 HTML：标题、`● 正在记录　最后更新 22:16:34` 都在，下面的
时间轴却只剩第一条，后面一小时凭空消失。等下一个 5 分钟才会自己恢复。

用户就是这样撞上的，还以为是丢数据 —— 磁盘上的 md 和 html 其实一条不少。

修法：`_atomic_write()` 先写 `xxx.tmp` 再 `os.replace()`。同分区内 replace 是
原子的，读的人要么看到旧的整份、要么看到新的整份，没有中间态。顺带给 `<head>`
加了 `Cache-Control: no-store`，避免走预览服务时拿缓存。

⚠️ 教训：**任何"定时写 + 定时刷新"的组合，都要假定读和写会在同一刻发生。**
先写临时文件再改名，成本几乎为零。

### 25. 证据堆在末尾等于没有证据；一天一张卡才叫"能翻的账"

用户连着提了三条意见，其实是同一个病：**结构没有跟着"人怎么回看"来设计。**

1. 录音、截图全堆在页面末尾一行"整场细节"里。21:26 的录音和 21:16–21:30
   那一段明明是一回事，却挨不着。改成每个节点自带 `**细节**` 行：录音按
   自己的起始时间归段，截图只挂**真正落在这一段内**的整点图（贪心取"最近
   的一张"会把 20 点的图挂到 22 点的节点上，点开牛头不对马嘴）。
2. 时间轴原来从早上往下排，打开第一眼看到的是十二小时前。改成**倒序**，
   最近的在最上面 —— `render_nodes(newest_first=True)`。
3. 一天开关机好几次，却被拆成好几块平铺。改成 md 照旧按"一次开机"存，
   HTML 按日期聚合成**一天一张卡**，默认收起，点开才展开。收起不是装饰：
   一天十几条节点全摊开，人只会扫一眼就走。

动画用 `grid-template-rows: 0fr → 1fr`，比 `max-height` 猜一个值稳；展开状态
存 localStorage，否则 5 分钟的 `meta refresh` 会把人刚展开的卡片踹回去。

顺带修掉两个会自己长出来的坏标题：模型有时只回一个软件名（"WorkBuddy"），
`len<4` 挡不住 10 个字符的英文名，所以再加一条"标题里必须有汉字"。

### 26. `file:///` 绝对链接在预览窗口里全被拦掉，看着像"链接坏了"

用户的原话："可点开 22:30 录音 / 22:31 录音 / 总账 / 代码档案 / 使用手册，
这些一个都点不开。"

链接本身是对的 —— 双击打开总账时它们全都通。问题在**打开方式**：

| 页面怎么打开的 | `file:///` 链接 |
|---|---|
| 双击 `总账.html`（file://） | 正常跳转 |
| 预览窗口 / 任何 http 服务 | 浏览器**静默拦截**，点了没反应 |

Chrome 系从 http 页面导航到 `file://` 一律拒绝（Not allowed to load local
resource），而且不弹任何提示，所以现象就是"点了没反应"，很容易被当成链接写错。

修法分两步，第一步想错了，第二步才对：

**第一步（错）**：把 `/reports/data`、`/reports/docs`、`/reports/_ext` 三个
**目录联接**（junction）挂到 reports 下，链接写成不带 `..` 的相对路径。
理论上目录联接在文件系统层面就是真实目录，应该能骗过静态服务。实测全 403 ——
服务在放行前会把 URL 解析成真实路径，越出根目录就拒，联接被拆穿了。

**第二步（对）**：把证据**硬链接**进 `reports\ev\`，链接就是 `ev/audio/…`
这种普通的相对路径。硬链接 = 同一份数据多一个名字，不占空间、删了不伤原件。
`os.link()`，跨分区才退回复制。

顺带摸清那个静态服务的三条规矩（用探针文件一条条试出来的）：

| 情况 | 结果 |
|---|---|
| `reports\根\xx.jpg` / `xx.wav` / `index.json` | 200 |
| `reports\子目录\xx.jpg` | 200（子目录本身没问题） |
| `reports\xx.md` / `xx.txt` | **404**（按扩展名拦） |
| `reports\data\…`（目录联接指出去） | **403**（realpath 越界） |
| 页面里 `file:///E:/…` | **静默拦截**，点了没反应 |

`.md` 一律 404 这条决定了文档必须转换：`docs\使用手册.md` 点开永远是死链，
所以 `_write_md_page()` 把 md 渲染成一个带样式的最小 html 再链过去。

`_rebased()` 在渲染前把 md 里**已经固化的** `file:///E:/…` 一起改写，
所以改成相对路径之前生成的老条目也跟着修好，不必重跑模型。

还有一个坑：`_write_md_page()` 一开始没建父目录，而 `_url()` 是在
`render_ledger()` 阶段就被调用的 —— 那时 `reports\ev` 还没创建，写文件抛
`FileNotFoundError` 被 `_url` 的兜底 `except` 吞掉，于是那一条悄悄退回
`file://`，混在一堆正常链接里很难发现。**兜底 except 会把"实现有 bug"伪装成
"正常降级"。** 现在 `_write_md_page()` 自己 mkdir。

验证方法（可复现）：直接对着预览服务的真实地址
（`http://127.0.0.1:端口/static-html/<hash>/`）把页面里每个 `href` 请求一遍。
最终 31 个链接全部 200、`file://` 残留 0 个。

⚠️ 教训：**本地页面里的绝对路径，等于把"只有双击打开才可用"写死进产物。**
而且"链接点不开"这种报障，先分清是**链接写错**还是**打开方式不支持**——
这次是后者，光改链接写法治不好，必须让文件真的待在被服务允许的目录里。

同样的问题也解释了为什么日卡摘要要换：原来是把最长的几个节点标题拼起来，
出来的是"查看 README 并静默运行录音、排查网络请求被拒…"这种流水账碎片。
模型写的那段总述，第一句本来就是主线，直接取它、压到 50 字，比拼标题准得多
（`_day_summary` → `_shrink`）。

### 27. 时间轴排版：所有对齐都挂在同一个 16px 上

2026-10-24 晚把时间轴从"左边一条线 + 文字往下堆"改成"圆点两侧交替 + 角标"。
几何上只有一条规矩：**圆点外沿到中轴的距离恒为 16px**，其余全部据它推出来。

| 元素 | 定义 | 依据 |
|---|---|---|
| 中轴 | `.tl-body::before`，`left:50%`、2px 宽 | 容器的水平中线 |
| 内容块 | `.card` 左节点 `margin-right:50%`、右节点 `margin-left:50%` | 边正好压在中轴上 |
| 圆点 | 左节点 `right:16px`、右节点 `left:16px` | 外沿离中轴 16px |
| 短横线 | `.dot::after` 朝中轴，宽 16px | 圆点外沿 → 中轴 |
| 角标 | `.lbl` 左节点 `margin-right:16px` + 右边框；右节点反之 | 边线正好接住圆点外沿 |
| 竖引线 | `.dot::before` 贴圆点外沿（`left:0`/`right:0`），高 16px | 圆点底 → 角标顶 |
| 内容起点 | `.card` `padding-top:72px` = 圆点 56 + 引线 16 | 字号行不被圆点压住 |

改圆点直径时**只改 dot 的宽高，别单独动那四个 16px**；`.card` 的
`padding-top` 也要跟着改（56 → 新直径）。只改一处，引线和角标就差 1~2 像素，
不放大看不出来，放大像手抖。

动画为什么这么写（都是踩过的）：

- **"时间轴变长"不靠动画高度**。`.day-body` 用 `grid-template-rows: 0fr → 1fr`
  拿到高度动画；中轴是 `.tl-body` 里的绝对定位元素（`top:0; bottom:0`），
  容器长它就长，全程不需要 JS 测量。这条决定了"节点多也不用手算高度"。
- 中轴另有一段 `scaleY(.001) → 1`（`transform-origin: top`），配
  `cubic-bezier(.22,1,.36,1)` 这种前段陡的曲线：200ms 内就到 1，之后只是
  跟着容器长。视觉上是"先画下来、再被撑开"，不会拖在内容后面。
  换成 `linear` 或 `ease` 就会明显落后于内容，像线没画到底。
- 延迟用**内联 `--i` 序号**算：`calc(var(--i) * 80ms + 60ms)`。
  不要用 `nth-child` 写八条 —— 节点数由模型切段决定，写死条数必然漏。
- 动画一律 `animation-fill-mode: backwards`，**不能用 `both`**：
  `both` 在结束后会一直压着 `to` 帧，`:hover` 的 `transform` 永远不生效。
- 进/出只靠 `.day.open` 一个类的增删，所以**收起再展开动画会自动重播**，
  不需要 JS 强制 reflow。`backwards` 还保证延迟期间元素是"未入场"状态。
- `prefers-reduced-motion: reduce` 时全部 `animation: none`，
  因为基础样式就是终态，关掉动画不会丢内容。

⚠️ 教训：**交替布局的每一处偏移都必须锚在同一个数上。** 圆点一个值、
短横线一个值、角标又一个值，各自"差不多"就是错位。

### 28. 时间轴的层级：轴在最外层，"天"才是轴上的节点

2026-10-24 深夜改。前面几轮把结构做成"一天一张可折叠的卡 → 卡里再放一根
事件轴"，结果是**轴套在天的里面**，一眼看上去分不清哪层是哪层。用户要的
正好反过来：

```
一根中轴（整页唯一）
├─ 10 月 24 日   ← 轴上的节点，带一句话，点开才长出当天明细
│    ├─ 22:21 → 23:10  调试启动脚本…
│    ├─ 22:06 → 22:21  排查网络…
│    └─ …（小一号圆点，同侧、同色系）
└─ 10 月 23 日   ← 轴上的另一个节点
```

判断层级的办法很土但管用：**看谁压在轴上。** 压在轴上的那个才是节点。
之前是事件压轴、天是卡片，现在是天压轴、事件是展开后的陪衬。改完把
`<section class="day">` 换成 `<li class="node day-node">` 直接挂进外层
`<ol class="nodes">`，`_render_session` 里那根内层轴去掉，明细改用
`li.node.mini`（小圆点 12px、不写字、时刻挪到 eyebrow），16px 规矩原样套用
（`.card` 的 `padding-top` 跟着直径改：60+16=76，12+16=28）。

**踩坑（这个坑值得单独记）：** 天节点的样式写成 `li.day-node .card` 这种
**后代选择器**时，会把展开区里 mini 节点的 `.card` / `.dot` / `.lbl` 一并
选中 —— 于是明细小点会被套上 60px 圆、天卡的 hover 光晕会整段点亮、
入场动画也会跟着重播一遍。改法：天卡一律用**直接子代**，
`li.day-node > .card`、`li.day-node > .card > .dot`。同理 JS 里取可点头部
要用 `querySelector(':scope > .card')`，否则会拿到第一个 mini 的 card，
点在明细上会误折叠。

其它两条沿用的教训：

- **层级变了，轴长会自动变**：中轴是 `.tl-body` 的绝对定位元素（`top/bottom`），
  谁把它撑高它就长到哪。所以"点开某天 → 轴跟着变长"不需要任何 JS 测量，
  `grid-template-rows: 0fr → 1fr` 撑高 li，轴就跟着走。
- **天节点左右交替用 `index % 2`**，不要用日期奇偶或别的规则 —— 用户看到的
  顺序是"新的在上"，交替只跟显示顺序有关。

⚠️ 教训：**嵌套展开结构里，样式选择器的深度就是层级声明。** 用后代选择器
写"这一层"，实际会把"下一层"也一起收进去；写 `>` 才是你说的那一层。

### 29. 4K 屏上"内容只占一小块"：写死的 px 是元凶，不是版心

总账第一版把所有尺寸都写死成 px：`max-width: 940px`、正文 12.5px、
天圆点 60px。在 1920 屏上看着正好，换到 3840 的 4K 屏上就成了屏幕中央
一条细线 —— 12.5px 在 4K 上物理只有 1/4 大，内容区只占屏宽 24%。

**改法**：`:root` 上挂一个 `--scale`，所有尺寸写成 `calc(基准 * var(--scale))`，
再用媒体查询按视口宽度换 `--scale` 的值。

```
:root { --scale: 1; }
main { max-width: calc(940px * var(--scale)); }
@media (min-width: 2560px) { :root { --scale: 1.6; } }
```

三个要点：

1. **基准尺寸全部套 calc，不留裸 px。** 留一个裸 px 就是一个"缩放时不变"
   的元素，会在放大的版面上显得格格不入。唯一该留裸值的是 `border: 1px`
   和断点阈值本身。
2. **16px 对齐的规矩必须整体等比缩放。** 坑 27 定的规矩是"圆点外沿离中轴
   恒 16px"，改响应式时如果只放大圆点、不放大引线和角标间距，几何立刻歪。
   所以 `calc(16px * var(--scale))` 要在**每一处**都写，不能只改圆点那一个。
3. **媒体查询用的是 CSS 像素，跟 Windows 显示缩放无关。** 4K 屏系统缩放
   100% → 视口 3840；缩放 150% → 视口 2560；两者都命中 `min-width: 2560` 档，
   而 150% 缩放本身已经把字物理放大过 1.5 倍，CSS 侧再缩 1.6 倍就过头了。
   **所以不能按物理分辨率分档，只能按 CSS 视口宽度分档。**

**宽度用 `clamp(最小, vw比例, 最大)` 而不是固定值**：超宽屏上如果死卡
1500px，两侧会留出巨大的空白；`clamp(1500px, 48vw, 2100px)` 让文字栏随
屏幕一起变宽，同时 2100px 封顶防止一行太长。

⚠️ 教训：**"看起来太小"和"排版不对"是两个问题。** 排版比例（左右各 50%、
16px 对齐）是对的，错的只是"物理尺寸没有跟着屏幕变大"。改的时候要分清
是缩放问题还是结构问题，别一上来就重排结构。

### 坑 #30 竖轴在宽屏上必然浪费屏幕（4K 上一行只放一天）

**现象**：照着年表做完竖轴之后，4K 屏上整页是一条细长的竖带，左右各剩
近 1000px 纯黑。做了 `--scale` 等比放大之后，用户一句"仍然两侧有大量的
空白黑边，只是调大了字体" —— 问题没解决。

**根因**：竖轴的结构决定了**一行只能放一个节点**。版心再宽，节点也只能
在左右两栏里交替往下摞，宽度用不上。这不是缩放问题，是**拓扑**问题。

**改法**：换成 S 形（蛇形折返）。节点排成网格，轴线顺着行间的通道来回
折返 —— 第一行左→右，第二行右→左。列数随视口变（860/1400/2100/3000 四个
断点，对应 2/3/4/5 列），版心 `min(98vw, 3600px)`。窄于 780px 时退化成
左侧单边竖轴，手机上依然正常。

关键几何：**每个格子左侧留 44px 轨道走廊、顶部留 46px 通道**。圆点骑在
走廊中线上，轴线只在这两条走廊里走，**不穿过任何卡片** —— 这一点决定了
它看起来是不是一条干净的线。同行的圆点 y 一致（因为格子顶部对齐），
折返时两点的 x 也一致（同一列），所以整条轴全是水平段和垂直段，
用一条 `polyline` 就能画。

⚠️ 教训：**"浪费屏幕"先问是不是拓扑问题。** 一根轴的容量是线性的，屏幕
宽度是二维的，只有让节点"折返"才能把第二个维度用起来。

### 坑 #31 越长的录音段，越可能压根不是人在说话

**现象**：10-24 23:13 之后，转写结果全线崩掉 —— 连续十几个小时，
每小时 2~3 段，几乎没有一段能识别出字。

**根因**：不是模型退化了，是**输入变了**。webrtcvad 只回答"这一帧响不响"，
回答不了"这是不是人说话"。机箱风扇、空调这类宽带稳态噪声能量足、时间上
连续，VAD 会一直判成语音 → 段永远不满足 `silence_close_ms` 的关闭条件 →
一路撑到 `max_segment_s` 被硬切开。

离线回放 240 段真实录音，结论非常干脆：

    段长 < 8 秒   → 有识别出字 69%
    8 ~ 15 秒     → 31%
    > 15 秒       → 12%

**改法**（三处，都在 `vquality.py` 和 `voice_recorder.py`）：

1. `max_segment_s` 30 → **12**。12 秒装得下正常的一句话，也是模型的甜区。
2. 到达上限时**在能量谷落刀**（`_cut_at_valley`）：在末尾 400ms 里挑能量
   最低的一帧切开，砍下来的那一截接着开下一段 —— 不丢内容，也不会把字
   拦腰斩断。PCM 要跟着 `truncate`，否则音频比数据库记录的时长长。
3. 结束前加一道**谐波性闸门**：浊音有基频，风扇没有。在自相关 2~12ms
   的滞后区间上取峰值高度，对有声帧取 75 分位。阈值 0.45 的实测效果：
   **清掉 93% 的无效段，同时留住 88% 的有效段**，单段判定约 25ms。

试过但没用的判据（别再走一遍）：频谱平坦度（人声和噪声都很低）、
能量动态（6.24 vs 5.15 dB，区分度不够）。

⚠️ 教训：**段长是结果，不是原因。** 看到"长段识别差"去怪模型，方向就反了；
长段之所以长，恰恰是因为它本来就不是该识别的东西。

### 坑 #32 转写文本能不能引用，只能按"容不容易错"分级

**现象**：总结里出现过"音响里有人在说'我我残'""俄我残隽"这类读起来像
故障的句子，源头是噪声段被解出的乱码。

**第一反应是写规则过滤乱码，试过，不行。** 用"没有虚词就判乱码"的规则，
会连"代理软件点击连接。""明天几十分？"这类完全正常但不含常见虚词的短句
一起误杀。**退一步：规则判不了对错，但能判"在什么条件下容易错"。**

**改法**：`_voice_trustable()` 三道 —— 时长 ≤ 12 秒、不含三个以上连续相同
的字、英文占比 ≤ 40%。通过的才允许模型复述大意，不通过的一律降级成
"有声音，但没听出能辨认的话"，prompt 里明确要求**那几句一个字都不许引**。

实测：86 句有文本的转写里，51 句可引述、35 句降级；降级掉的正好是
"我。""如果。""小是截屏录音录上显示的信息而不是当中的的动的有效信息确并
没有证加。"这批。

⚠️ 教训：**宁可少引，不可错杀。** 写错一句话比漏写一句话更难接受 ——
用户看到自己"说过"一句从没说过的话，对整个系统的信任就没了。

### 坑 #33 单实例锁挡不住"两个人同时启动"

**现象**：2026-10-25 凌晨发现，语音链路整整跑了两套 —— 两套 recorder 同时
开 WASAPI 麦克风、两套 asr 同时写库、两套 daemon 互相看不见对方。它不报错、
不崩溃，安静得像一切正常，只有识别结果悄悄变差。

**根因**：原来的单实例锁是"锁文件 + 心跳 + 查 pid"三件套，看着很严，实际
挡不住两人同时启动 —— **两边都在对方写盘之前读到了旧内容，于是都判定
"没人跑"，双双继续。** 这个窗口只在开机自启和手动双击撞上的那一刻出现，
之后再也复现不出来。

**改法**：加内核级命名互斥（`vcfg.acquire_mutex`），谁拿到谁跑，第二个进去
立刻返回。原来的文件锁留作第二道。

写的时候踩的坑（很容易写错且不易察觉）：

```python
k = ctypes.windll.kernel32                      # ✗ 拿不到 GetLastError
k = ctypes.WinDLL("kernel32", use_last_error=True)  # ✓ 必须这样
```

普通 `windll` 调用之后 ctypes 不会替你留 `GetLastError` 的值，于是
`ERROR_ALREADY_EXISTS`(183) 永远看不到，第二个实例照样觉得自己抢到了。
**第一版就是这么错的，而且同进程内测不出来**（Windows 互斥在同一线程是
可重入的），必须开两个独立进程测：A 抢到 / B 拒绝 / A 退出后 C 能抢。

⚠️ 教训：**"看起来很严的锁"和"真的挡得住"是两回事。** 凡是"读完再判断
再写"的序列锁，都要问一句"两个人同时读到旧值会怎样"。

### 坑 #34 一夜没关机，"今天"就永远不出现

**现象**：用户 10 月 25 日早上问"今天已经 25 日了，总账怎么没有新增一个节点，
还是在 24 日上总结"。

**根因**：session 的日期标题用的是 `t0`（**开机时刻**），而 live 模式每次都把
"当前这一场"从开机总结到现在。24 日 20:48 开机的机器一夜没关，25 日早上这一跑
总结的还是同一场 —— 日期照样写 24 日，25 日凌晨的内容全并进 24 日账上。
**只要不重启，新的一天就永远不出现新节点。**

**改法**：`build_facts` 增加 `live` 语义 —— 开机早于当天 0 点时，把窗口起点
抬到 0 点，真实开机时刻记在 `carry` 里。于是：

- 25 日 00:05 那一跑生成的是**25 日**的条目（`00:00 起 · 进行中`），
  boot_key = `202610250000`
- 24 日 20:48 那条的 key 是 `202610242048`，从此不再被覆盖，自动固化成历史
- 标题写成 `00:00 起（接 10 月 24 日 20:48 的开机）`，不写"20:48 开机"——
  日期已经是 25 日了，再写 20:48 会被读成"25 日晚上八点开机的"，与事实相反

配套还要处理**封存**：24 日那条最后一次被写是在它自己的 23:5x，标题里留着
"进行中"。不封的话总账上永远挂着一个昨天还在跑的会话。`_seal_stale()` 把
昨天及更早、还写着"进行中"的条目改成 `24:00 结束` 并按开机时刻重算时长，
正文一个字不动。

**踩的两个坑**：

1. `_BOOT_RE` 原来只认 `HH:MM 开机`。标题改成"起"之后 key 抠不出来，
   同一天的条目会**每天新增一条而不是替换**，总账瞬间变成流水账。
   正则必须同时认两种格式。
2. 单次开机的天数卡在 `_render_day` 里，跨天括注（"接 24 日 20:48 的开机"）
   只在**一天有多个 session** 时才显示（`show_mark=multi`）。25 日只有一个
   session，这句话就被吞了，用户看到"25 日 00:00 起"还是不知道是昨晚的延续。
   改成从天节点卡面上直接提取。

⚠️ 教训：**"按天汇总"和"按开机汇总"是两个不同的时间轴。** 前者问"这一天干了
什么"，后者问"这一场干了什么"。混用一次的代价是：用户不重启，你就永远少一天。

### 坑 #35 亮度、梯度都分不开"壁纸"和"窗口"

**现象**：截图右半边是大片桌面壁纸（麋鹿、河、树林），用户认为是无效图像。

**第一个念头全是错的**：

| 念头 | 为什么错 |
|---|---|
| 按亮度切 | 壁纸有亮天空和暗山林，比窗口里的灰底文字对比还大 |
| 按梯度切 | 壁纸是照片，细节丰富；实测拉伸压缩后某些区域梯度仍达 10+ |
| 只截活动窗口 | Windrecorder 有这个开关，但代价是**并排两个窗口只截有焦点的那个**，用户明确不接受 |
| 检测纯色区 | 壁纸不是纯色，是照片 |

**真正分开它们的是灰度双峰度**：一个 40 像素的小块里，窗口内容（黑字白底、
图标、按钮）往往同时踩着深浅两极端，灰度直方图呈**双峰**；壁纸的灰度是连续
过渡的，**单峰**。实测三张截图：内容区双峰度 16~30，壁纸区 2~3（正常分辨率下
15~17 对 21~29），一条阈值切开。

阈值取 `均值 - 0.5*标准差`，不是中位数：壁纸块占大多数，会把均值拉低，
减半个标准差正好落在两个峰的中间；用中位数会把壁纸纹理也点亮。

再叠一道**行列投影**取外接矩形，且投影只认成片的 —— 某行的内容块数不到
最大值 1/5 就不算内容行，专门剔掉壁纸里那几块高对比区域（亮天空撞暗山林）。

三条安全绳：

- 裁完还剩 85% 以上面积的，认为"本来就没多少空白"，**直接不裁**（全屏看文档
  正是这种情况）
- **原图永不删除**，裁出品是旁边的 `.crop.jpg`，胶囊里挂一个弱化的"原图"
  小链供核对
- 只在原图变新时才重裁（判 mtime）—— 实时模式 5 分钟一轮，不判的话每轮都把
  历史截图重算一遍

还有一个坑：**改 `_url` 只对新条目生效**。HTML 是从 md 渲染的，而 md 里的链接
在写入那刻就固化了。历史的截图要一起受益，必须在渲染前（`ledger_to_html` 的
`_rebased` 旁边）统一替换一遍。

⚠️ 教训：**"没有内容"和"内容长什么样"是两件事，后者常常没有简单的判据。**
亮度、颜色、梯度这些直觉指标在照片面前全部失效；能用的往往是分布形状
（双峰 vs 单峰）这类不看绝对值的特征。

### 坑 #36 蛇形换行：反转 order 排不出蛇，部分行会被塞到左边缘

**现象**：S 形时间轴上线画对了，节点位置不对 —— 2 列时 25 日在左上、24 日在右上，23 日却落在 25 日正下方（左列），轴线还得从右上斜拐到左下。用户描述得一字不差："当一行放不下时，23 日应该在 24 日的正下方；假如有 22 日、21 日，22 日在 23 日的左边，21 日在 22 日正下方。"

**根因**：最初用 CSS `order` 实现蛇形 —— 按"第 0 行左→右、第 1 行右→左"的走访顺序给每个节点发 order 值，指望自动放置能摆出蛇形。但**自动放置永远从左往右填格子**，order 只能改"谁先填"，改不了"填哪个格子"。后果：

- 只有**整行填满**时碰巧是对的（第 1 行满员，从左填=从右填）
- **部分行必然错**：最后一行剩 1~2 个节点时，全部被左对齐塞到行首 —— 23 日跑到 25 日正下方
- 轴线按走访顺序连圆点，还会画出交叉的斜线

**改法**：放弃 order，按蛇形坐标**显式写 `grid-row` / `grid-column`**：

```js
items.forEach(function (d, i) {
  var r = Math.floor(i / c), j = i % c;
  if (r % 2 === 1) j = c - 1 - j;   // 奇数行从右往左
  d.style.gridRow = String(r + 1);
  d.style.gridColumn = String(j + 1);
});
```

落完位，**轴线按 DOM 顺序连圆点就是一条 S**（DOM 顺序 = 时间倒序 = 蛇形走访顺序），不用再单独算走访序列。列数变化（resize）时跟着重算。

验证不靠眼睛（无头浏览器不可用）：把渲染产物里真实的 `place()` 源码抽出来，用 Node 配 mock DOM 跑，断言用户给的全部场景（c=2 n=3 时 23 在 24 正下方；c=2 n=5 时 22 在 23 左边、21 在 22 正下方），再加一条通用不变量 —— **相邻两天只能"同行相邻列"或"同列下一行"**，保证折线只横只竖、没有斜线段。测试留在 `test_serpentine.js`。

⚠️ 教训：**`order` 调的是"顺序"，grid 自动放置调的是"填充方向"，两者都改变不了"格子坐标"。** 要精确落位就得显式给坐标。另外"满行碰巧对、部分行露馅"这类 bug，测试必须覆盖 `n % c != 0` 的情况 —— 用户举的例子（3 天 2 列）恰恰就是部分行。

### 坑 #37 谐波闸门把"活动声"也一并丢了（啼哭/脚步/水声全灭）

**现象**：用户要求"尽量"认出人类活动声 —— 小孩啼哭、挪动凳子、走动、
打开水龙头。一查链路，这些段**根本到不了识别**：谐波闸门（坑 #31 立的功）
按"无声带周期性振动"整段丢弃，而除了啼哭（恰好有谐波），挪凳子、走动、
水声全是宽带非谐波，历史上 100% 被当噪声毙掉。

**根因**：谐波性回答的是"有没有人在**说话**"，不是"有没有**人**"。
这两个问题在风扇噪声上答案一致（都没有），在活动声上分道扬镳。
用一道只管说话的闸门去管所有声音，必然把一类有价值的信息筛掉。

**改法**：两级架构（`vevents.py`）。

- 第一级 DSP 粗筛在录音进程跑（纯 numpy，20ms/段，可放音频回调）：
  脉冲个数、单次重击上升沿、高频占比+持续度。三条路任一中招就留，
  打 `flag='event'` 落库。**原则是宁可错放** —— 键盘会被放进来，
  但那只多花一秒推理，精度交给第二级。
- 第二级 AST（`MIT/ast-finetuned-audioset`，AudioSet 527 类）在转写进程跑，
  映射中文标签。实测（72 条 ESC-50 真实样本）：啼哭 3/3、脚步 3/3、
  倒水 3/3、刮擦（手锯代理）3/3、敲门 3/3；键盘/鼠标/风扇/风雨/洗衣机
  零误报；冲水声认不出（顶分 0.05），不硬凑。

**试过又删掉的两条粗筛规则**（都记在 `vevents.SCREEN_DEFAULTS` 注释里）：

1. "稀疏+亮+间隔短 = 键盘点击"否决：真实啼哭/吱嘎/倒水的脉冲间隔也是
   0.21s，和键盘完全重叠 —— ESC-50 上 1/3 的啼哭被它误杀。
2. "3~30Hz 调幅峰度 = 刮擦"：洗衣机峰度 57.9、手锯 40~82，同一量级，
   分不开，只会把风雨声全放进来。随机噪声的包络功率本来就铺满 0~50Hz
   （10ms 包络的奈奎斯特只有 50Hz），"占比"类指标对噪声天然失效。

**合成信号喂不动 AST**：初期用合成脚步/水声测第二级，全被判白噪声 ——
AST 没学过假声音。精度断言必须上真实样本（ESC-50 从 hf-mirror 的
`ashraq/esc50` parquet 抽，72 条），合成信号只用来钉 DSP 粗筛的留/毙。

⚠️ 教训：**"提高精度"和"提高召回"是两个方向，后者常常要新建一条通路。**
闸门越准，漏掉的那一类越彻底；补召回不能靠放松闸门（噪声跟着进来），
要么加一级只负责"别误杀"的粗筛，要么换一个能回答新问题的模型。

### 坑 #38 懒加载的模型，被先 import 的库偷了缓存路径（静默退化）

**现象**：e2e 测试里 AST 一切正常，接进真实 worker 后却每条活动声都没标签。
日志里只有一行 warning：`Can't load feature extractor for
'MIT/ast-finetuned-audioset-10-10-0.4593'`，然后"活动声只剩 DSP 粗筛" ——
功能还在，只是精筛静默消失，不报错、不崩，肉眼只看结果根本发现不了。

**根因**：`huggingface_hub` 在 **import 时**就把 `HF_HOME` 环境变量算进
`constants.HF_HUB_CACHE`。转写进程里 funasr（SenseVoice）先 import 它，
等 `vevents` 被懒加载时再 `os.environ["HF_HOME"]=...` 已经晚了 ——
模型明明已缓存，查找路径却还是默认的 `~/.cache`，于是判定"没有"，
退回（不通的）huggingface.co。单独跑 vevents 的测试永远复现不了，
因为那时它第一个 import，路径是对的。

**改法**：`vevents` 在设完环境变量后，直接改已 import 的常量兜底：

```python
import huggingface_hub.constants as _hfc
_hfc.HF_HOME = _HF_HOME
_hfc.HF_HUB_CACHE = os.path.join(_HF_HOME, "hub")
_hfc.ENDPOINT = os.environ.get("HF_ENDPOINT", _hfc.ENDPOINT)
```

⚠️ 教训：**"环境变量控制库行为"只在 import 之前设才有效。** 多模型共存的
进程里，懒加载 + 别人先 import = 缓存路径/端点/离线开关全部可能失效，
且失败模式是静默降级。要么在进程入口（任何重依赖之前）设好环境，
要么像这样直接 patch 常量；测试则必须覆盖"真实加载顺序"（先 SenseVoice
再 AST），单独测模块永远抓不到。

### 坑 #39 虚线图案是按旧路径长度量好的：一展开，轴线断成一截一截

**现象**：用户报"把时间节点展开要看详情时，时间轴的线，竖线就断了，
断断续续，节点直接没连接了"。

**根因**：轴线用 `stroke-dasharray` 做 1.2 秒的"生长"动画，虚线图案在
载入时按**当时的路径长度**量好就再也没重算过。可展开一天会把下面几行
整个顶下去，页面长出滚动条时列宽还会收窄 —— **路径一变长，多出来那截
正好落进虚线图案的空隙里**（SVG 的虚线是"实线 L、空隙 L"循环）。
于是竖线后半段消失、最远的节点看着没连上。收起反而看不出问题
（路径变短，全落在实线段里），所以只有"展开"这一侧暴露。

单行布局也会中招：三天排一行时展开不挪点，但滚动条一出现，列宽收窄
几个像素，路径长度就变了，尾巴同样掉进空隙。

**改法**（`vdigest.py` 的 `_PAGE` 脚本）：

1. 动画播完（1.4 秒）**立刻撤掉虚线换实线**（`solid()`），稳态不留侥幸；
2. 这期间几何只要有变化也马上转实线，不硬撑动画；
3. 非入场重画一律 `strokeDasharray = 'none'`；
4. 顺手把无单位的 `dasharray = len` 改成 `len + 'px'`（CSS 里长度必须带单位）；
5. 刷新机制从"定时刷固定 900ms"改成**续期制**（几何还在变就续，稳住才停）
   + `ResizeObserver` 兜底，凡是布局变动都追得上，不再靠猜时长。

⚠️ 教训：**"按初始尺寸量好的视觉参数"都是定时炸弹。** 虚线、遮罩、
裁剪区、`getTotalLength()` 量出来的任何东西，只要布局会变，就必须在
每次几何变化时重算，或者在稳态下彻底撤掉。另外这类 bug 在窄视口才现形
（宽屏三天排一行，点不挪），测试要同时覆盖"多行折返"和"单行+滚动条"
两种几何。

**复现测试**：`node test_timeline.js` —— 同样从渲染产物里抽出页面脚本，
配虚拟时钟 + mock DOM 跑，覆盖入场动画、展开变长、收起变短、空闲零写入、
入场中途突变、单行+点位移六类场景。为确认测试不是空转，另造了一份
"旧脚本"变体验证：同一场景下旧代码 `dasharray` 停在 1000 而路径已 1400，
正是用户看到的断线；新代码 17 项全过。

### 坑 #40 合并条目只带第一个 wav：搜索和文字稿必须落到"段"

**现象**：要做"找到当时的录音 + 文字稿"时，发现 `voice_lines()` 把同一人
连着的话并成一条（为了避免一句话一条），合并条目里只有**第一段**的
`wav`，后面几段的音频和文字都在条目里漂着，拿不到段 id。

**根因**：合并是**展示层**的需求（读着顺），段才是**证据层**的单位
（一个 wav 一段文字）。两层数据混在一个对象里，展示层一合并，证据层
的粒度就丢了。

**改法**：每条合并条目挂一个 `segs` 列表，每段自带
`{id, start, end, dur, text, wav, labels, emotion}`。展示层照旧合并，
搜索索引、文字稿、明细里的链接全部按段取。

顺带两个坑：
- `voice_lines()` 的 SQL 原来没 `SELECT s.id`，加段 id 时才暴露出来；
- 明细里的"文字稿"链接**不能**只靠检索索引那一轮生成 —— 索引有天数
  上限（页面要内联），老条目会链到不存在的文件。所以
  `_ensure_transcript()` 在渲染链接时就地保证文件存在。

⚠️ 教训：**"合并"和"定位"是两种粒度。** 只要上层做过合并，下层的证据
就必须保留原始粒度，否则任何"点开这一段"的需求都会撞墙。

### 坑 #41 中文没有空格：停用词表按整词匹配等于没匹配

**现象**：搜"帮我找找"，理解行显示关键词是「帮我找找」—— 停用词表里
明明有"帮我"和"找找"，却一个都没消掉。

**根因**：`STOP` 是空格分词后整词比对，而中文查询没有空格，
"帮我找找"在整个串里是一个词，`STOP.indexOf("帮我找找") < 0` 永远成立。

**改法**：分词后对每个词的**头尾反复削多字停用词**（单字不动，否则会把
"戳""礁"这类真词削残），"帮我找找"→"找找"→"" 整条丢掉。

⚠️ 教训：中文的停用词过滤**不能假设有分词**。要么按边缘修剪，要么先跑
一遍 n-gram 切分；直接整词比对在中文上是个空转的过滤器。

## 十、排错速查

**症状：时间线一条都没有**
1. `probe` 看麦克风峰值。几十 → 麦克风问题（回去看坑 1）
2. 看 `recorder.log` 尾部有没有 "段 #N ... 语音占比="。有 → 录音正常，问题在查询时段
3. 看 ASR 进程是否活着；`asr.log` 有没有新记录
4. 直接查库：`SELECT COUNT(*) FROM segment WHERE start_ts > strftime('%s','now')-3600;`

**症状：有段但没文本**
`asr` 进程可能卡住或崩了。`SELECT s.id FROM segment s LEFT JOIN asr a ON a.segment_id=s.id WHERE a.segment_id IS NULL;` 有结果就是积压了。手动跑一遍：`voice_asr.py --once`。

**症状：说话人被标成"其他"**
跑 `voice_enroll.py --from-segments <id> --explain`，看相似度落在哪。
- 0.30–0.55 → 灰区，说明是同一个人但条件差异大（远场、情绪激动、感冒）
- < 0.30 → 基本不是同一个人

**症状：进程数不对但不是 0**
守护进程在退避重启中，看 `daemon.log` 里 `%s 退出 (code=...)` 那行的 code。连续快速失败会退避到 60 秒一次。

**症状：整个库想推倒重来**

### 8.8 想调搜索（日期怎么认、关键词怎么打分）

三个地方，按改动频率排：

| 想改什么 | 动哪里 |
|---|---|
| 日期/关键词解析规则、停用词、打分权重、结果长什么样 | `vsearch_ui.py` 的 `SEARCH_JS`（页面里跑的那段，改完重新生成总账即生效） |
| 搜多少天、每段正文截多长、语音/屏幕段上限 | `vsearch.py` 顶部的 `SEARCH_DAYS` / `TEXT_CAP` / `MAX_ITEMS` / `MAX_SCREENS` |

`vsearch.py` 管数据和文件（取段、写文字稿、拼索引），`vsearch_ui.py` 管
解析和渲染（纯字符串常量），`vdigest.py` 里的 `_search_block()` 负责把两者
接起来并内联进页面。三者分工是为了改解析规则时不必翻渲染代码。

**为什么索引内联而不放 json**：总账是双击打开的（`file://`），Chrome 在
`file://` 下 fetch 本地文件会被 CORS 拦掉。所以索引必须写在页面里，
`SEARCH_DAYS` 的上限也就跟着有了意义。

### 8.9 搜索没搜到想要的东西

按顺序查：

1. **看输入框下面那行小字** —— 它显示"理解：日期 X · 关键词 Y"。
   日期或关键词不对，就是解析问题（`SEARCH_JS` 里的 `parse()`）。
2. **超过 21 天** —— 索引只覆盖最近 `SEARCH_DAYS` 天，老日子不进索引
   （时间轴里照样能翻，明细链接也有效）。
3. **录音没转写出文字** —— 搜索只能搜"识别出来的文字"和屏幕标题/OCR。
   那段要是噪声段，文字稿页会明说没有文字。
4. **关键词被停用词削光了** —— 比如问"我找了什么"，"找了"不在停用词表
   但整串削完可能只剩噪声。直接说实词（"越南""窗帘""敲击"）最稳。

`.venv` 的 `python.exe` 靠 `pyvenv.cfg` 里的 `home` 找到基座 Python
（uv 装在 `%APPDATA%\uv\python\...`），整盘拷到没装那个路径的机器上
直接起不来。**便携 Python 的正确合成方式**：uv 基座目录（79 MB，
本身是完整独立 CPython）+ venv 的 `Lib/site-packages` 合到一个目录，
跳过 `include/ libs/ tcl/ Scripts/`（头文件/静态库/Tk/命令行入口，
运行时一样都不碰，一律 `python.exe script.py` 启动）。torch 是 CPU
版（venv 里没有 nvidia_* 包），搬到没独显的机器也能跑。

### 13.2 坑 #43：`distutils-precedence.pth` 是哑弹

venv 的 site-packages 里有这个 .pth（uv 建环境不带 setuptools 留下的），
它 `import distutils_hack`，而 distutils_hack 不在 —— 拷进便携 Python
后每次启动都可能刷一条无害的 import 失败。构建时按名字跳过。

### 13.3 坑 #44：`find_device` 抛异常 = 守护进程每小时崩一次

配置钉着开发机的 "USB 2.0 Camera"。换机器后 `find_device` 直接
`raise`，守护进程的重启循环每小时试一次、每次抛，日志一片红，用户
只看到"录不到音"。改成：找不到就退到第一个输入设备（优先原接口），
日志写明换了谁。**录到音比录对音重要。** 配套的 `vprobe.py --write`
在安装时就把对的设备写进 config.json，运行时回退只是兜底。

### 13.4 坑 #45：抽取器钉死 3:1，非 48k 设备全线失效

`_DECIM` 是 48000→16000 的三级半带 FIR。新机器的麦原生 44.1k 的话，
抽出来是 14700Hz，模型全乱。修法不是改抽取器（那是验证过的热路径），
是在 `on_frame` 前加 `soxr.ResampleStream` 在线搬到 48000，48k 机器
一行都不执行。**新增分支必须让默认路径字节级不变。**

### 13.5 坑 #46：历史数据换盘，链接不会自己修

`voice.db` 的 `wav_path` 和总账 md 里固化的 `file:///E:/...` 都是旧机器
的绝对路径。原样拷到新电脑，录音链接全死。`vrepath.py` 干这件事：
数据库按表按列 `replace()`，文本文件按字节 replace（编码无关），
二进制按扩展名跳过。安装器通过 `payload/data/ORIGIN_ROOT.txt` 知道
旧根路径。DB 快照用 `VACUUM INTO` 拿，直接拷 .db+.wal 可能拿到半笔事务。

### 13.6 坑 #47：.bat 的中文路径按 OEM 代码页读

UTF-8 存的 .bat 里写"总账.html"，在中文 Windows（cp936）下读出来是
乱码、文件找不到。两个规避：① .bat 内容全 ASCII，中文只出现在文件名
（NTFS 存 UTF-16，不受代码页影响）；② 需要碰中文路径的动作（打开总账）
交给 `open_ledger.py` —— Python 按 UTF-8 读自己的源文件。install.ps1
必须带 UTF-8 BOM，否则 PS 5.1 解析器按 ANSI 读，中文串直接语法错误。

### 13.7 Windrecorder 从硬编码改成可配置

`voice_timeline/vsnap/vclean/install_autostart` 里五处硬编码
`E:/AI/Windrecorder`，统一改为读 `config.json` 的 `windrecorder_dir`
（留空回退老路径）。语音链路本来就不依赖它：指不到位置就当没有屏幕
数据，录音/转写/活动声/总账照常。**可选组件绝不许堵死主链路。**

### 13.8 冒烟测试为什么用包里自带的一段录音

新机器上房间可能安静，录 8 秒可能零段，ASR 就验证不到。所以包里塞了
一段 2.6 秒的真人短句（`tools/asr_smoke.wav`，本项目自己的录音），
`voice_asr.py --file` 直接验证 SenseVoice 真的能转出字 —— 确定性证据，
不靠环境运气。用户可随时删掉它。

### 13.9 坑 #48：SQLite 给同一列多个 SET 赋值，后者盖回前者

`vrepath.py` 第一版这么写：

```sql
UPDATE segment SET wav_path = replace(wav_path, 'E:/AI/voice', '新'),
                  wav_path = replace(wav_path, 'E:/AI/voice', '新')
WHERE ...
```

跑完打印"416 行已更新"，数据一个都没变。两个原因叠在一起：
① SQLite 的多个赋值**都基于原值计算**，第二个 replace 看到的是旧串、
   把第一个的结果整个盖回原样；
② `changes()` 按"处理过的行数"计数，**不比对新旧值**，所以谎报成功。

修法：多个 replace 套在一个表达式里层层传递
`SET wav_path = replace(replace(wav_path, ?, ?), ?, ?)`。
教训：**"它说改了多少行"和"数据真的变了"是两件事**，迁移类脚本必须
换连接重读验证（`vrepath.py` 就该自带一步复检）。

## 十四、版本号与自动更新（2026-10-25，1.0.0 起）

`vupdate.py`（约 600 行）是更新器，`build_package.py --bump`
是发布入口，`VERSION` 文件是版本号唯一源头。

### 14.1 坑 #49：SQLite 多赋值盖回原值（已在 13.9 记，这里补关联）

`vrepath.py` 的教训同样适用于更新器：任何"它说改了多少行"
都不能当真。`vupdate` 的所有写操作后都跟一步**换连接重读**
（`verify_staging` / `verify_local` / apply 成功前的复检），
测试里专门造了"改一个字节"和"删文件"两个用例盯这个
（test_update.py 复检一节）。

### 14.2 坑 #50：venv 的 manifest 语义差一半

发布包 manifest 是 `payload/code` 布局算的，安装树是
`ROOT/code` 布局。两侧内容一致 → 签名一致，但**测试第一版
拿 `build_manifest(inst)` 生成安装树 manifest**，inst 下没有
`payload/` 子目录，算出来全是空签名，复检全红。
教训：布局不同的两份数据，"同一份 manifest"是安装时**拷贝**
过去的，不是各自算的。check/verify 的三方（发布包、安装树、
manifest）必须同源。

### 14.3 坑 #51：回滚只回 parts，不回 manifest = 复检永远红

apply 失败/手动 rollback 时只 rename 回了 code 目录，根级的
`manifest.json` 还是新版的 —— "新清单 + 旧文件"，之后
`vupdate verify` 永远报不符，用户以为系统坏了。
修法：备份目录里加 `_rootfiles/` 快照，回滚时一起还原。
rollback 收集 parts 时记得排除 `_rootfiles`（它不是 part）。

### 14.4 坑 #52：守护进程不能在自己进程里更新自己

`auto` 模式第一版打算在守护进程的检查线程里直接 apply ——
三个死结：① apply 要停守护进程，停的就是自己， STOP 文件
没人响应；② 替换完要拉起新代码，但单实例 mutex 还攥在旧进程
手里，新实例抢不到锁直接退出；③ 冒烟测试跑 30 秒，主循环
心跳停滞。
正解：线程只负责**发现**，发现后 `Popen` 一个独立的
`pythonw vupdate.py apply --auto`，然后写 STOP 让自己退场。
旧进程先彻底退出（mutex 释放、daemon.lock 删除），独立进程
才动手替换，完事用 start_voice.vbs 拉起新代码的自己。
**"换自己的发动机"必须下车换，不能在车上换。**

### 14.5 自动救援为什么放在写锁之前

`voice_daemon.main()` 里 `vupdate.auto_rescue()` 必须在
`already_running()` 和写 `daemon.lock` **之前**：回滚流程里的
`stop_daemon()` 会读锁文件判断"有没有人在跑"。要是我们已经
写下自己的 pid，它会把我们自己的心跳当成别人在跑，然后
死等 40 秒超时。放在前面，回滚看到的是上个进程留下的旧锁
（pid 已死 → 判定没人在跑 → 直接回滚），回来后 main 照常
启动，两不相扰。

### 14.6 分级签名的精度取舍

`part_sig(part, content=False)` 对 python/models 只按
"路径+大小"算：改内容不改大小的文件会漏。之所以敢这么干 ——
这两个目录由 build_package.py 整体产出，包里没有任何机制
单独修改其中文件；而逐文件 sha256 一遍 3.4GB 要好几分钟，
检查更新就成了负担。`code` 目录反过来：必须 content=True，
它是唯一会被人手动改的部分，且只有 700KB。
**分级精度按"谁会动它"分配，不按大小。**
